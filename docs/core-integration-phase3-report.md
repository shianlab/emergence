# 核心整合第三阶段：意图、能力发现与任务规划

日期：2026-10-30。对应 `emergence-core-integration-plan.md` 第三阶段。实施范围为 Agent 核心与现有中文检查入口，未改动 Logo、配色或页面布局。

## 已交付

1. **按任务复杂度分流**：简短问答直接进入原执行循环；具体修改使用轻量提示；明确规划、多步骤、跨项目等请求进入结构化规划。初始分流是本地启发式，语义解释和方案选择由当前窗口所选模型完成，没有另起一次预处理模型请求，也没有自动启动九个代理。
2. **结构化任务契约**：目标、约束、验收、非目标、假设、关键未知、候选方案、冲突、选择理由、证据引用及最多 12 个步骤。关键问题只允许标记为影响结果、权限或路线；阻塞未知使计划进入“需要关键补充”。
3. **实际能力盘点**：模型配置与凭据存在性、工具的真实作用域与激活条件、Skills 的模型调用开关、MCP 初始化/断开状态、内置方法、执行角色和窗口绑定。登记、连接、候选可用与调用回执分开显示；不把上游依赖登记伪装成本机服务。
4. **计划检查与执行边界**：拒绝循环/缺失依赖、虚构能力、无效角色、角色模型不匹配、失效的窗口/会话/项目/模型绑定、独立模式跨窗派发和虚构读取回执。复杂任务在计划有效前不能写入、运行 Shell 或派工。有效计划仍必须通过原权限系统，不能绕过用户审批、显式拒绝、继承权限或文件规则。
5. **现有调度器衔接**：主控模式下，计划可选择已配置的执行窗口；派工继续使用 `emergence_dispatch` 与既有任务契约/调度/验收机制。不会自行创建窗口、切换模型，也没有增加第二套执行循环。
6. **预算和会话内恢复**：默认规划前最多 12 次原生读取、4 次计划提交；规划必需上下文预算 16000 字符。计划本体预留上下文空间，证据索引按剩余空间加入。计划按实际会话和项目分别保存，恢复只恢复方案，不能自动重放副作用或把方案标成已完成。待回答的关键问题得到补充时保留原目标。
7. **内置方法实际使用**：从已校验目录选取 Conductor、Scout、Artisan 的职责摘要参与复杂任务提示；其余治理角色仍按各自后续阶段落地。没有安装或执行附件中的 Skill、Hook、安装器或外部运行时。

## 本机使用

- 重新启动 `Emergence`，自然输入任务即可。明确说“先规划……”可进入规划路径。
- 输入 `/`，搜索“规划”，或直接 `/plan`：查看目标、验收、未知项、方案取舍、证据回执、步骤能力及窗口/模型/会话绑定。
- `/capabilities`：查看实际能力及状态；没有凭据、未连接、未通过激活条件或仅供人使用的 Skill 不会被标成可调用。
- `/tasks`：查看真正派发的任务。`/plan` 展示的方案不是完成证明。
- `/core off` 关闭观察与规划；`/core observe` 恢复核心。只关闭规划可在配置中设置 `core.planning.enabled=false`，再 `/settings reload`。

旧配置自动获得兼容默认值：

```json
{
  "core": {
    "mode": "observe",
    "planning": {
      "enabled": true,
      "researchCalls": 12,
      "revisions": 4,
      "contextChars": 16000
    }
  }
}
```

观察器仍不授予权限；`observe` 沿用第二阶段模式名，第三阶段规划由单独的 `planning.enabled` 控制。规划记录保存在配置目录的 `core/plans/<会话与项目摘要>.json`，含任务和方案文本，属于本地会话数据，不是长期记忆。保存前使用现有凭据脱敏；损坏文件和链接目录不会被覆盖。

## 验证与修复

运行 `npm run inspect:core3`。机器记录：`artifacts/core-phase3/inspection.json`；中文菜单、窗口隔离和窄屏帧：`artifacts/core-phase3/native.json`。

验收包括 12 组检查：类型检查、本机构建、全部单元/Harness 集成、第三阶段中文菜单、第二/第一阶段回归、模型/历史/角色选择器、实际文件/Shell/Skill/MCP 与 OpenAI/Anthropic 本地协议、API 故障恢复、16 会话并发、Windows ConPTY 输入和工具审批。

新增 11 项规划专项测试；与原有 81 项合计 92 项单元及 Harness 测试。专项覆盖：

- 简短问答和具体修改各只发起一次模型请求。
- 未规划写入被拒绝，实际读取、提交有效计划后才执行。
- 缺失能力、关键未知、伪造证据、循环依赖和模型/窗口绑定检查。
- 预算耗尽、格式错误重试、后续权限收紧及执行窗口会话更换。
- 排队消息在被执行循环领取之前不会覆盖当前目标。
- 实际 Skills 注册/调用策略、真实本地 MCP 进程连接与断开。
- 有效多窗口计划通过原有调度器派发，并进入既有待验收状态。
- 会话方案恢复、损坏文件和目录链接防护；工作目录变化保留目标并作废原证据。

开发巡检中发现并修复：多窗口重复注册同名工具；Harness 在 pre-step 前解析工具导致新规划工具首步不可见；读取预算在权限复查时误拒绝最后一次有效读取；新直接任务未持久清除旧方案；能力清单忽略工具激活条件；执行窗口收到主控新契约时残留旧个人规划；工作目录变更后遗失原目标。

## 明确边界

- 本阶段验证使用真实 Harness、Windows 终端、本地受控模型协议和真实本地 MCP 进程；没有调用付费模型 API，没有把模拟模型的方案质量当作实网模型能力证明。
- 本地分流可能误判任务复杂度；模型规划质量仍取决于所选模型。工具不支持或计划不完整时只应解释缺口，不能假装完成。
- `verified` 仅表示本任务有成功工具回执，不是对任意后续参数、服务健康、事实正确性或整个任务的认证。模型凭据存在不等于网络连通；MCP 的连接标记来自插件初始化/关闭状态，不是持续健康探针。
- 16000 字符是新增规划上下文的预算，不是整个 Harness 历史、所有工具输出或模型总 token 上限。已有会话日志仍保留完整交互；计划记录不执行自动长期记忆写回。
- 步骤范围和验收条目是可审查的模型方案，实际路径、权限、派发与任务验收仍由原有运行时负责。本阶段没有将方案变成新的持久执行 DAG。
- 下一阶段仍是第四阶段：可靠执行、恢复与决策审批；本次未提前实施第五阶段的长期记忆和进化闭环。
