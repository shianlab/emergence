# Emergence 安装与更新体系改进方案

日期：2026-11-17。基线：已发布 1.01（包版本 1.0.1）。

状态：第一至第三阶段代码和本机隔离验收已完成，见[第一阶段](installation-phase1-report-2026-11-17.md)、[第二阶段](installation-phase2-report-2026-11-17.md)及[第三阶段报告](installation-phase3-report-2026-11-17.md)；外部电脑与正式发行验收留待第四阶段。建议下一正式版本为 1.02 / 1.0.2，不替换已发布的 1.0.1 资产。当前职责见[安装维护说明](structure/installation-maintenance.md)与[在线更新维护](structure/update-maintenance.md)。

## 一、目标与核查结论

目标是让普通用户一次安装后能启动、能得知新版本、能更新、能回退，并且不会积累无限量的旧安装文件。安装更新属于发行基础设施，不交给模型、Skill 或会话执行循环完成。

用户截图证明下载发行包时连接失败，显示目标版本为 1.0.0。它不能单独证明是 TLS、代理、运营商链路或服务端的问题，也不能说明安装后修复的具体原因。用户已说明拿不到对方报错与修复记录，此历史个案保留为原因未确认；不继续要求用户找记录，也不将新增安装检查等同于已复现该问题。

| 已核实事实 | 证据位置 | 影响 |
| --- | --- | --- |
| 引导脚本固定默认版本为 1.0.1 | 根目录 `install.ps1` 的 Version 参数 | 旧脚本不知道新版本，安装入口与发布版本需要人工同步 |
| ZIP 及校验文件均只下载一次 | `install.ps1` 的 Invoke-WebRequest 调用 | 短暂断线即失败，没有自动重试或续传 |
| 每次使用新的临时目录，退出时删除 | `install.ps1` 的 temporaryRoot 与 finally | 下载失败后再次执行通常从头下载 |
| 下载进度被关闭 | `install.ps1` 的 ProgressPreference | 下载较慢时用户难以分辨等待和卡住 |
| 1.0.1 ZIP 为 225,257,067 字节，文件清单有 31,100 项 | 已发布资产及本地安装 manifest.sha256.json | 除网络外，小文件解压、复制、扫描也有成本 |
| 构建直接复制完整生产依赖树 | `emergence/scripts/release-pack.ts` | 生产依赖不等于本产品所有启动路径实际都用到，需做依赖闭包核查 |
| 安装先检查源文件、复制到 stage，再检查 stage | `emergence/release/manage.cjs` | 有完整性保障，但多次遍历与复制的成本需要测量和优化 |
| 安装操作还递归检查已有安装根目录 | 同上，noLinks(root) | 累积旧版本会增加检查工作量；不能直接删除链接检查，应缩小到实际接触的受管路径 |
| current.json 在修改 PATH 前切换 | 同上，atomic(current) 与 updatePath 的调用顺序 | PATH 失败可能出现“报错但版本已切换”；现有错误提示对旧版本保留的表述过强 |
| 没有候选版本实际启动探测 | 同上 | 文件完整并不证明依赖、启动入口和系统环境正常 |
| 仅有 install / uninstall 操作 | 同上 | 没有统一的 update / rollback / repair / 旧版本保留策略 |
| TUI 和 CLI 没有版本发现服务 | `emergence/src/app/cli.ts`、工作台命令入口 | 用户不会得知更新 |

发行包包含 LibreOffice 组件、语音组件、检查界面等较大的上游依赖。当前 CLI 使用 `@deepseek-ai/dsh-base` profile，顶层 dsh 包又声明大量其他 profile 和工具依赖。必须沿实际 profile、插件注册和动态加载关系查证，不能根据包名判定“没用”后删除。

上一轮本机与匿名公开下载安装验证通过，只证明当时该机器、该网络与该发行物的路径能跑通，不代表其他机器和弱网条件已验收。本次未重跑完整功能矩阵；这是安装专项核查。

## 二、确定的产品行为

### 安装

用户复制一条官方命令，看到“检查环境 → 下载 → 校验 → 部署 → 验证启动”的进度。失败明确说明失败阶段、是否可直接重试、日志位置。重试复用可验证的下载内容。

安装完成必须确认程序能启动。没有模型密钥时明确进入首次配置流程；它与程序文件损坏是不同状态。数据分析的可选 Python 环境缺失，不应阻止普通 CLI 安装成功。

### 更新提示

每次启动可触发后台检查，但使用共享缓存限频；持续运行时定期检查，优先在空闲边界展示提醒。建议默认缓存有效期 6 小时，单次发现请求最长 5 秒。手动检查可绕过缓存。

不在每条对话都请求服务器，不让每个分屏单独下载。网络不通不阻塞启动或发送任务。只传版本、平台等必要请求信息，不上传对话、项目路径和密钥。

界面提示示意：`发现新版本 1.02 · 查看更新说明 · 立即更新 · 稍后`。默认通知，由用户选择安装；也可关闭自动检查。CLI 自动化输出不混入提醒文字。

拟提供 `emergence update` 和 `/update`；实际参数与帮助、斜杠推荐一起实现。这些是计划中的命令，当前 1.01 不支持。

### 更新、回退与清理

新旧版本分别存放。先准备新版并验证，再切换统一启动入口；不逐文件覆盖正在运行的版本。当前任务继续运行，界面提示“更新已就绪，下次启动生效”。

默认保留当前版本、上一份通过验证且兼容的回退版本，以及仍有进程使用的版本。其余受管版本在确认未使用后清理。无法可靠判断占用时延后清理，不强制终止用户任务。

模型配置、加密密钥、会话、记忆、项目目录与用户数据环境不属于安装清理范围。回退程序也不能把用户数据回滚覆盖；未来若发生不可逆数据格式升级，必须明确回退兼容范围，不能承诺任意版本可退。

## 三、四阶段实施顺序

### 第一阶段：首次安装可靠性与速度

1. 为当前链路补齐分阶段计时：下载、解压、文件验证、复制、系统入口更新、启动探测。保留可分享的脱敏诊断日志。
2. 实现有上限的重试与退避、连接/总耗时限制、清晰进度。优先采用 Windows 可用的下载能力，兼容 PowerShell 5.1；不能假定每台机器都有最新版 curl 参数。
3. 使用产品专属下载缓存，并锁定同一资产的下载操作。以版本和哈希标识完整包；部分文件单独保存。处理不支持 Range、远端内容改变、错误页返回 200、缓存损坏等情况。只在完整校验通过后安装。
4. 断线保留有用的部分下载；错误或过期缓存按明确规则清理。缓存有空间/时间上限；同样检查路径、链接与所有权。
5. 分析真实运行依赖闭包。仅剔除有证据证明不使用的依赖和资源，保留许可证；动态加载、原生模块、KIM、Code/Data、Skills、MCP 和模型配置均纳入回归。
6. 优化解压到部署的路径，尽量减少完整文件树的重复复制；完整性和路径安全检查继续存在。优化前后同机对比，不预先承诺未经测量的秒数或体积。
7. 加入安装健康探测：固定运行时、CLI 版本、关键原生依赖、Harness 启动就绪、模型配置程序依赖和命令入口。探测不用真实 API 密钥，不产生模型费用。
8. 缺失/损坏受管安装文件提供明确修复路径；不覆盖用户自己的同名目录，不将 PATH 冲突误报为下载失败。

交付：可靠的一行安装与离线安装、分段性能报告、弱网测试记录、安装诊断。

验收门槛：干净 Windows x64 用户环境无开发版 Node/npm 也能安装；中文用户名、空格路径、重复安装可用；中断后可恢复或明确安全重下；损坏包不能进入当前版本；安装成功后立即验证能启动。对方“装完还要修复”的问题须有复现与验证记录，缺少记录时列为待确认，不能写已解决。

### 第二阶段：统一升级事务、修复与回退

沿用现有 versions、current.json、安装锁和所有权检查，提取职责明确的安装服务，不再为各入口分别增加一套更新脚本。

统一状态流程：

```text
发现目标版本 → 获取资产 → 验证 → 暂存部署 → 启动探测
           → 完成入口准备 → 原子切换当前版本 → 记录结果 → 清理可删除版本
```

1. 安装、更新、修复、回退共用状态转换、安装锁和错误分类。持久记录操作阶段，使崩溃恢复能分辨“尚未启用”和“已启用但未清理”。
2. 解决当前 PATH 与版本指针的提交顺序问题。启动器及管理器自身升级也纳入兼容与恢复边界，不能只保证 current.json 原子写入。
3. 启用前失败，旧入口保持可用；启用后探测失败，恢复有效旧入口并记录原因。清理失败独立显示，不把健康新版误报成安装失败。
4. 同版本损坏修复必须先准备完整替代副本，并保护运行中的实例；不能在用户使用中的目录直接删改。
5. 对运行版本建立可校验的占用记录，结合进程身份处理异常退出和 PID 重用；覆盖 TUI、CLI 批处理和原生模型配置工具。
6. 提供显式回退入口和只清理受管目录的保留策略。删除前验证绝对路径、安装标记、链接及占用。
7. 托管安装、便携包、源码/开发安装明确区分。开发目录不自动覆盖；自定义启动器不擅自替换，显示对应更新方式。

交付：一套共享安装服务、更新/修复/回退入口、旧版本和缓存清理策略、故障恢复记录。

验收门槛：模拟部署失败、PATH 写失败、磁盘不足、启动失败、切换时崩溃、并行升级；每个失败点都有可用旧版本或可解释的恢复入口。更新前后配置、密钥和用户历史保持一致；仍被使用的版本不能删除。

### 第三阶段：版本发现与 TUI 提醒

1. 发布小型稳定版清单：协议版本、产品、平台、语义版本、资产 URL、大小、哈希、更新说明及最低安装器要求。默认不接收预发布版本，不按字符串大小比较版本。
2. 安装和检查使用同一发行清单，指定版本仍使用不可变发行物。无需依赖匿名 GitHub API 的有限配额，也不从 README 或 package.json 猜版本。
3. 限定可信 HTTPS 来源、重定向目的域、响应大小和超时；检查清单字段与资产对应关系。哈希仅证明完整性，不冒充发布者签名。自动更新发布前补齐清单签名与可信公钥方案，并验证密钥轮换/失效处理。
4. 一个安装级服务负责缓存、限频、请求取消和检查状态；工作台只订阅投影。多个进程通过锁协调，多个分屏不重复请求。关闭工作台释放定时器/监听器。
5. 启动检查、定期检查、手动检查共用服务。提示支持 Enter 选择、Esc 延后、查看更新说明、关闭自动检查；不恢复任何跨窗口控制能力。
6. 更新执行交给第二阶段的同一服务。显示真实下载/验证/部署状态，不把“检测到新版”显示成“更新成功”。
7. `doctor` 展示安装来源、当前/可用版本、最近检查和更新失败原因，避免要求用户把密钥交给其他 Agent 修复。

交付：版本清单与发布校验、后台检测、中文更新提示、命令与帮助接入。

验收门槛：启动与聊天不被慢网阻塞；断网、代理错误、限流、坏清单不影响原功能；同一版本不过度提醒；更新进行中可继续当前任务；自动化 JSON 输出不污染；伪造、签名错误、平台错误资产拒绝启用。

### 第四阶段：完整发布与旧用户迁移验收

1. 覆盖从 1.00、1.01 升级，以及全新安装、重复安装、便携使用、自定义目录、PATH 冲突、运行中更新与回退。
2. 网络矩阵涵盖断线恢复、不支持续传、超时、下载截断、错误代理、校验不符、断网启动；使用可控故障注入，不依赖恰好遇到真实断线。
3. 安装矩阵覆盖 PowerShell 5.1 / 7、CMD 启动、新终端和当前终端、中文用户名/空格目录、无 Node/npm 的 Windows 环境。桌面人工验证仍由用户完成，不接管桌面。
4. 回归原有核心功能与完整检查矩阵，确认打包裁剪没有破坏 KIM、工具、Skills、MCP、Code/Data、独立分屏及原生模型配置。
5. 在至少一台实际外部电脑验证从官方入口安装、启动、配置模型与完成一次任务。记录实际阶段耗时，不能用开发机器成功替代这项证据。
6. 发行顺序固定为：构建和验收 → 上传不可变 ZIP 与校验/签名 → 匿名下载验证 → 发布说明 → 最后更新稳定版指针。防止客户端提前看到不存在的资产。
7. 文档与 GitHub 更新日志同时更新，提供一条新用户安装命令、一条旧用户迁移命令和故障诊断入口。保留 1.01 作为兼容回退基线。

交付：1.02 发行候选、完整验收报告、更新日志与旧用户迁移说明。实际发布需基于该候选全部验收结果，不能在未验证时替换当前下载入口。

## 四、状态与模块归属

2026-11-17 进度：第一至第三阶段已完成本地实现和对应验收，分别见[第一阶段报告](installation-phase1-report-2026-11-17.md)、[第二阶段报告](installation-phase2-report-2026-11-17.md)和[第三阶段报告](installation-phase3-report-2026-11-17.md)。第四阶段按用户最新要求完成本机验收与 1.02 候选包，外部电脑和正式发布暂缓；见[第四阶段报告](installation-phase4-report-2026-11-17.md)。GitHub 与实际用户安装保持原版本，稳定版清单尚未发布。

| 职责 | 唯一所有者 | 不应承担的工作 |
| --- | --- | --- |
| 发布清单、资产、签名、稳定版指针 | 发行构建与发布流程 | 不携带用户配置或凭据 |
| 下载、校验、安装事务、回退、清理 | 安装管理层（从现有 release/manage.cjs 演进） | 不运行模型、不操作会话任务 |
| 检查缓存、通知偏好、版本比较 | 安装级更新服务 | 不在每个窗口保存一份权威更新状态 |
| 提示、进度与用户选择 | CLI / TUI 适配层 | 不直接删目录、改 current.json 或修改 PATH |
| 模型配置与密钥 | 现有配置/凭据服务 | 不被安装清理或默认配置覆盖 |

偏好与下载缓存分别落入明确的更新专属存储，不随意向严格的模型配置 schema 增塞字段。迁移要一起完成实现、调用方、状态归属、测试、资源释放、打包清单和旧入口退出。

## 五、必须说明的边界

- **现有 1.00 / 1.01 没有检测代码，不能凭远端发布让它们自行弹出提醒。** 用户需手动升级一次到带更新机制的版本，此后才能持续收到提醒。
- 断点续传、包体优化和重试能降低失败成本，但不能保证被阻断的 GitHub 网络一定可用。若实测仍受限，需要正式、可维护的官方镜像/CDN；不默认引入未知第三方下载站。
- 暂不引入差分补丁安装。先把完整包安装、事务升级与回退做可靠，避免同时增加补丁链和多版本组合复杂度。
- 启动健康、外部模型连接、可选数据环境是不同验收项；不能把全部混成一句“可以使用”，也不能将首次配置 API key 称为程序修复。

## 六、参考依据

[Claude Code 官方安装与更新说明](https://code.claude.com/docs/en/setup#auto-updates)描述了启动和运行期间检查、后台安装、下次启动生效，并区分安装来源。借鉴其生命周期与安装来源判断，不照搬其他产品内部实现。Emergence 首版拟默认通知后由用户选择更新。

[curl 官方手册](https://curl.se/docs/manpage.html)用于核对重试、续传参数的行为与组合限制；实施仍需匹配 Windows 实际可用版本并做回退测试。
