# 第三阶段专项方案：派工可靠性，分五批实施

日期：2026-11-12。基线提交：b124fc1。第三阶段仍未完成。本方案细化原第三阶段，不增加总阶段数，不提前进入第四阶段。本轮只形成方案，不修改生产行为、不发起新的付费调用。

## 一、验收为什么失败

这些结论来自代码与 artifacts/iteration-20261112-phase3 的实测记录，不以模型自述判断。

| 问题 | 证据与归因 | 状态 |
| --- | --- | --- |
| 原始要求与改写文本被重复合并 | planning-service.submit 将 analysis、旧 plan、新 plan 的 constraints/acceptance 按原文 Set 合并；相同意思的不同措辞仍算多条，而领域列表上限为 12。GLM 跨项目第二轮出现 constraints 超限后规划耗尽预算 | 已确认的工程问题；包含上一轮新加保护逻辑引入的问题，需要替换 |
| 主控菜单与执行职责不一致 | 首轮模型看到 pwsh，调用后被主控门禁拒绝 | 已修复，并验证首步隐藏、切回独立模式恢复；继续作为回归门槛 |
| 两种验证路径叠加 | DeepSeek 对照模型提交四个普通任务：两项实现、两项依赖实现的复核；宿主又为普通任务安排独立验证/审查，观察结束时共七条任务，含三条 assessment。followthrough 对每个主任务要求 review 与 verify | 已确认存在重复职责与额外链路；不能仅据此断言十分钟全部耗时都由它造成 |
| 规划预算耗尽 | GLM 同项目两轮、跨项目两轮均无任务成功入队，约 187–189 秒后结束；默认 planningMs 为 180000 | 结果已确认；必须继续区分模型响应、上下文规模、被拒调用与修订消耗，不能概括为“模型慢”或只放宽阈值 |
| 已派发但未完整收尾 | DeepSeek 主控约 34.1 秒派出四项任务，部分实现与审查成功；600 秒观察截止时未 completed，记录八次具体工具批准 | 不是“完全派不出去”，也不等于整体可用；审批观察时间、模型调用与冗余验证需要分别归因 |
| 单窗口边界 | Code 两轮成功；数据两轮中一轮达到 120 秒测试观察期限 | 独立运行能力有成功证据，但不足以声称所有独立任务均稳定；观察超时不等于生产任务执行超时 |

现有本地确定性测试验证了预设正确/错误协议下的执行规则。真实模型会改写需求、拆出多余步骤、选择不同工具并产生不稳定延迟，因此全部本地测试通过不能替代真实闭环验收。当前没有证据证明所有失败都来自窗口匹配算法；匹配、准入、执行和收尾必须分开取证。

## 二、统一目标与代码边界

用户提交自然语言任务 → KIM 理解并形成带版本的需求 → 模型提出交付步骤 → 宿主校验、分配并持久化 → 执行窗口完成 → 宿主安排必要验证/审查 → 汇总真实结果。

模型负责理解和建议；宿主负责需求版本、资源匹配、权限、去重、状态与完成判定。主控模式默认主动协调，独立模式由各窗口处理自己的请求；窗口多不等于必须协作，独立请求也不能被主控自动征用。

沿用现有 TaskLifecycle、TaskScheduler、TaskExecution、CorePlanning、TeamCoordinator/Followthrough、CoreAssurance；每一类规则只有一个负责人。任何新契约必须迁移工具定义、模型输入、运行校验、持久化、测试和帮助。删除被替代的业务分支；兼容入口只转换输入。

## 三、五批实施与各自验收

### 3A：需求契约与计划准入——先消除“计划反复失败”

负责：core/domain 的需求/计划契约、planning-service、tool-protocol、PlanStore 及任务契约构造。

1. 保留用户原文引用及摘要，宿主为已接纳的要求分配稳定 ID、来源和版本。语义理解仍可由模型提出，但 ID、版本、来源校验由宿主管理。
2. 把“已接纳要求”与“模型新增建议”分开。计划引用 requirement IDs/version，主要提交步骤及所覆盖要求，不再逐轮抄写整套约束与验收。模型改写现有要求不能创造一条新的宿主要求。
3. 新增建议必须保留来源和冲突检查；用户明确更改目标才更新对应需求版本。必要澄清只针对影响结果、权限或路线的缺口，不要求用户为每条普通任务重复确认。
4. 删除现有按三份文本 Set 合并的逻辑。以每请求和每步骤的真实上下文预算约束规模；超预算在派工前给出具体缺口，不截掉必需要求，不无限追加列表。
5. 一套 schema 生成可见参数与运行校验；错误包含字段路径、原因、仍保留的要求引用及可修订内容。同一请求的修订预算和原始约束持续有效。
6. 涉及存储形状变化时采用显式版本与迁移：备份、旧记录读取、损坏拒绝、回退限制均测试；不得用旧 v1 标签写入旧程序无法理解的新语义。

退出条件：同一要求连续改写/修订不会膨胀计数；引用不存在或过期要求不能执行；遗漏关键验收、任意新增授权、越界范围被拒绝；合法修订在同一任务内可成功派发。用已有 GLM 失败输入做回放；先完成这批再改调度策略。

### 3B：主控分配与独立模式——确保“派给对的窗口”

负责：work-allocation、task-admission、team-coordinator、task-coordinator 与 planning adapter。

1. 准入使用有版本的实时窗口快照：项目、会话、模型、可用工具、权限、角色偏好、接管状态、队列和运行负载。先筛硬约束，再比较负载与偏好；不能把角色名称当作实际能力证明。
2. 主控提交简洁工作图，宿主绑定窗口/会话/模型和项目范围。事务提交前复核快照与权限，失效则取消本次准入并重新判断，不把旧计划发给新会话。
3. 统一自动、手动派工和恢复入口的幂等规则：同一请求同一图只入队一次；重复回调、双提交和保存失败不得重复执行。
4. 区分暂时忙碌、被接管、目录不匹配、缺能力及权限拒绝。暂时无资源可等待且显示解除条件；永久缺口明确阻塞，不能把“准备派工”显示成“已派工”。
5. 独立窗口保留直接使用；设为主控才自动协调其团队。关闭主控、接管、关闭窗口、切模型时，历史执行绑定不变，新任务重新评估。单步任务不为了利用窗口而强拆；可并行步骤才并行，同文件写入按现有锁串行。
6. 精简主控不必要的工具菜单和重复背景，保留必需要求、证据与权限；首步菜单与执行门禁一致。

退出条件：覆盖 2/3 窗口，同/不同项目，同/不同模型，忙闲/隐藏/接管，依赖与相同文件冲突。用户只发原始任务，不补“请派工”；目标窗口、范围和验收绑定正确。独立窗口不受协作任务误占用，保存失败或取消后不产生额外工具执行。

### 3C：验证与收尾——确保“做完能正确结束”

负责：任务契约、CoreAssurance、team-followthrough、执行证据与任务结算。

1. 区分用户要求的交付任务、用户要求的研究/检查任务，以及宿主为完成判定生成的审查任务。检查本身是用户交付目标时保留，不能按 reviewer/verifier 名称一刀切删除。
2. 主控工作图仅描述主要交付和必要业务依赖；宿主验证图统一生成。若模型提交与宿主流程重复的验收步骤，按明确任务类型和关联对象处理并给出反馈，不按关键词偷偷删步骤。
3. 审查唯一键至少绑定被审对象、产物版本、检查种类与规则版本，保证同一检查不会因轮询或重复事件重复创建；依赖关系不得形成互相等待的环。
4. 验证负责实际运行检查，审查可引用同版本有效验证回执并完成自己的独立读取。复用的是有来源、权限范围和版本绑定的证据，不是模型说“已经检查过”。产物变化必须失效；必要独立审查标准不降低。
5. 完成汇总由宿主计算：必需交付、规定的验证/审查及最终产物版本全部满足，且没有不确定副作用，才能 completed。失败、待审、取消都不能被成功总结覆盖。
6. 有限修复保留原失败证据；修复后只重跑失效检查。审查生成器不再对它自己产生的审查递归生成整套审查。

退出条件：两项简单实现只产生规则规定的必要检查，不出现重复审查链；可从实际任务图解释每个节点的必要性。测试迟到回执、重复事件、部分失败、产物被修改、审查拒绝、修复预算及重启。全部交付满足后自动收尾，无需用户再发“继续/总结/验收”。

### 3D：时间、审批和失败恢复——确保“等什么、为什么停，都说得清”

负责：run-budget、planning-service、task-budgets、执行/模型事件适配及现有状态展示。

1. 记录排队、模型等待/生成、工具执行、审批、暂停和总历时；定义并发重叠的归属，不能把多个并行工具时间简单相加冒充墙钟耗时。缺少供应商阶段信号时如实保留未知，不推测时间。
2. 总预算仍为上限，另设各阶段可诊断期限。持续输出不自动无限续期；模型重复计划不算工作进展。先消除重复上下文/调用，再依据测量决定配置是否合理。
3. 状态显示具体任务和窗口、正在等待的条件、已用时间和处理途径；沿用当前 TUI 视觉，不重做 UI。审批拒绝明确停止相应动作，不通过换窗口或换模型绕过。
4. 网络错误只有在确认尚未执行副作用、且供应商与应用重试总额有界时才重试。写操作结果未知先核对回执/产物；暂停恢复不重放历史写入。模型切换只遵循用户配置的规则，不静默替换供应商。
5. 测试观察期限与生产预算分开。测试触及期限写出最后状态和时间分解，并可靠停止该测试拥有的进程；不遗留后台付费请求，也不把未观察到完成写成生产失败或成功。

退出条件：慢响应、静默响应、网络中断、工具阻塞、用户迟迟未批准和队列拥堵均可区分；等待审批不会被误计为工具执行；取消后没有未归属执行，重启后无自动重复副作用。

### 3E：固定构建验收——证明这次真正可用

1. 先跑失败回放、确定性完整回归和故障注入；真实测试前固定源码/产物 hash、供应商模型配置、输入样本、观察期限、Token/调用预算和输出目录。中途改构建，该轮标记失效，不与修复后样本拼接。
2. 主矩阵：独立单窗口、同项目主控多窗口、跨项目主控多窗口 × GLM/DeepSeek 两种主控配置 × 每格连续两次，共 12 个基础任务。独立样本两次分别覆盖小型 Code 与数据计算；团队样本包含不同模型执行窗口，覆盖 2 与 3 窗口。观察预算依据 3D 实测预先登记，禁止失败后临时放大凑通过。
3. 另做两个独立窗口并行、批准/拒绝、取消重启、无可用窗口和真实工具失败的回归；这些可以确定性测试为主，不为重复安全边界无限消耗 API。
4. 发一次自然语言任务即可进入正确流程；除任务本身必需的审批/澄清，不允许验收人员补工具参数、手动指定任务 ID、追加“请派工”或发命令替 Agent 收尾。受控测试审批逐项记录，只在用户配置的权限范围内。
5. 正向样本要求正确产物、实际检查、总任务 completed、无重复执行、无越界；负向样本要求正确阻塞/拒绝/取消及可解释状态。基础 12 个正向样本全部通过才关闭本阶段。两轮是本轮准入门槛，不是对任意任务成功率的统计承诺。
6. 任一正向失败须归因到具体批次并修复，相关矩阵在新构建重跑；保留原始失败。交付用户可运行样例与中文复现步骤，不能只有测试数字。

## 四、实施纪律、兼容与产物

- 顺序固定 3A → 3B → 3C → 3D → 3E；每批都完成代码、调用者迁移、必要测试和主动巡检，再报告。下一批不能被用来掩盖上一批未完成。
- 每批围绕所属模块提交，不在 TUI、提示词和 catch 中各放一份相同业务规则；不新增第二个队列或第二套任务状态。迁移时明确删除旧实现。
- 新需求版本/审查键等若改变持久化语义，先写迁移与备份测试，再启用写入。现有历史数据与外部兼容协议有明确边界，不承诺旧程序可以写回新格式。
- 每批记录完成项、失败修复、测试范围、未覆盖项、可回退提交和数据回退限制。已修复的菜单问题继续回归，不重复当作新成果。
- 第三阶段只有 3A–3E 全部通过才完成。此方案不承诺模型永不出错；要求框架不制造重复/错派，正常样本闭环成功，异常可解释、可取消、可恢复。
