# 第二、三阶段联合巡检与修复

## 结论

现有结构保留单一任务状态入口、单一调度器、Harness 执行循环和原权限边界。本轮发现并复现了原测试未覆盖的取消时序和主控角色切换问题，已在各自责任模块修复；没有新增调度队列、重复执行器、状态存储或自动批准机制。

本机新版已构建，375 项回归及本轮本地终端/HTTP 检查通过。可以据此继续第四阶段。上一冻结构建的付费模型矩阵为 12/12；本次修改后的构建未重跑付费矩阵，仍需用户真实项目试用，不能把旧矩阵称为新版的真实模型验收。

## 已复现的问题及统一修复

| 优先级 | 原因与实际影响 | 修复及证据 |
| --- | --- | --- |
| P1 | 派发记录保存后，读取依赖证据还会异步等待；用户在等待期间取消，原执行路径未再次核对任务归属，继续向已解除绑定的窗口投递任务。隔离复现实际产生了 1 次取消后的写入 | `TaskExecution` 将依赖观察与状态提交分开；观察后、投递前复核归属，最终核对会话/目录/模型/租约。跨项目取消、接管、迟到读取失败均为 0 模型请求、0 写入 |
| P2 | 轮次结算在多个异步观察之间写入 result，取消已完成后，旧回调仍能覆盖取消原因，显示“实际写入完成” | 结果与产物版本先在局部收集，最后核对执行归属后一起写入；已终结任务不再被 `finishWithoutTurn` 重复结算。回归验证取消回执原样保留，原本已发生的写入仍保留台账且不重放 |
| P2 | 界面设置主控、核心配置、取消主控各有不同状态列表。`blocked` / `interrupted` / `needs_review` 历史记录可永久阻止切换，而 cancel 对这些记录不再生效 | 统一到 `Collaboration.assertConfiguration`，使用已有任务终结语义，不改写历史记录。工作台仅调用核心预检；模型切换后核心再次检查 |
| P2 | 仅检查未结束的子任务，遗漏子任务结束到自动审查之间仍活跃的总目标；此时能够切走主控，留下失去协调者的目标 | 同一配置检查同时保护活跃总目标、主控运行和待审批。总目标终态统一到 `settledCoordinationPhases`。保留同主控增补执行窗口；显式取消协调后可正常切换 |

新增两个测试文件、8 个用例：`tests/dispatch-lifetime.test.ts`、`tests/team-reconfiguration.test.ts`。测试通过可控异步屏障复现时序，使用实际 Harness、工作台入口及临时项目文件，不以等待固定时长碰运气。

- 静态盘点 153 个 TS/TSX/Python 源文件，27472 行；核心反向依赖 app 为 0，字面量导入的运行时循环为 0。动态拼接导入和事件连接不能仅靠这一统计证明正确，已重点核对编排与审批事件入口。
- 任务字段仍由 `TaskLifecycle` 修改；`TaskScheduler` 管队列与并发；`TaskExecution` 管 Harness 投递/回执；`TeamFollowthrough` 管总目标后续协调。此次修复沿这些职责落点完成。
- 规划草稿仍是 `PlanStore` 中的方案，不是第二套执行状态；完整准入后才进入原任务图。请求错误恢复仍由原 Harness 请求级重试负责，业务任务不自动重放。
- 审批仍取原所属会话队列，按版本、参数和权限绑定答复；没有因测试失败降低权限、放宽文件范围或绕过 read/工具审批。
- JSON 文件替换、各存储自己的 schema/租约、旧格式迁移分别保留。取消与存储异常不能用伪造成功状态处理。
- 修复前后清单对比：只改变 5 个生产模块，新增 2 个测试文件，没有删文件或改依赖。变更清单按本轮开始时的哈希比较，区别于此前尚未提交的 R1–R5 改动。
- 更新了维护说明与项目入口中的旧路径和格式检查范围，原始历史验收记录保留。

仍需关注的维护热点：`workspace-ui.ts` 约 1652 行、`controller.ts` 约 1154 行、`planning-service.ts` 约 1064 行、`task-coordinator.ts` 约 900 行。现有检查不代表这些文件没有复杂度债务。第四阶段接触对应功能时，按“交互呈现 / 会话权限 / 规划准入 / 生命周期”职责提取可单独验证的模块；避免只按行数拆文件，或给同一状态增加第二套管理对象。本轮不进行与已复现问题无关的大范围搬移。
