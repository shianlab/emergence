# 3C：验证与收尾

日期：2026-11-12。基线：3B `bb8ffdd9`。结论：本批完成；3D、3E 和第三阶段整体验收尚未完成。

## 行为与结构

1. 新的引用式计划要求每个步骤明确填写 `purpose`：`delivery` 为交付，`user-check` 为用户要求的研究/检查交付，`assurance` 为宿主核验。后者可用 `subject` 指明被核验步骤，准入返回 `HOST_OWNS_ASSURANCE`，要求主控移除重复节点及引用再提交。没有按名称、关键词或 reviewer/verifier 角色删任务；用户的研究、审计报告、测试交付继续保留，并引用原需求验收编号。此元数据只用于提案准入，执行计划继续使用已有交付契约，宿主任务仍由 `assessment` 明确标识。
2. 同一被审任务、产物/运行版本、核验种类、规则版本只生成一个审查键。版本也包含原任务权限。并发申请等待同一次提交后重新校验各调用者；排队、执行中、成功或失败的同版本记录均被复用。重复请求不会重跑失败核验；应核对缺陷并修复原交付，再核验新的修复任务。保存失败撤销、取消、原派发会话和独立窗口约束继续有效。
3. 核验版本采用稳定序列化，避免存储恢复时字段顺序变化造成重复核验。旧执行日志的摘要算法不变，只对新核验身份使用稳定摘要，避免扩散修改历史日志契约。
4. `CoreAssurance` 统一判定证据：逐项覆盖验收要求，核对引用是否存在、所属任务/运行/会话是否一致、输入/产物是否仍有效。实施验证仍须实际成功的命令回执；只读研究使用实际读取证据。审查保留独立读取，可参考同版本通过的验证，无需重复执行 Shell。缺失回执不能通过空数组的 `every()` 被误判有效。
5. 总任务收尾统一调用 `CoreAssurance.completion`。交付必须成功、已验收、有成功报告且没有不确定副作用；独立核验须有有效证据，相关在途任务必须结束。最后重新核对最终文件版本及任务/核验记录。模型总结不能把待审、取消或失败改成成功。
6. `completion-evidence.ts` 单独负责产物依赖关系。后续交付覆盖同一文件时，必须是明确的依赖后继，且最终交付有自己的核验；前序证据只可在该依赖链内作为历史阶段证据保留。没有依赖关系的多写者不以“最后完成时间”决定可信版本；独立读取同一文件且哈希一致时视为同一最终版本，不误判覆盖冲突。修复/恢复链保留原依赖关系。数据分析的输入、定义和报告仍按原生回执严格复核。
7. 沿用原队列、权限门禁、修复预算和生命周期。修复保留失败记录，只为新的失效交付重新核验，其他未变化的交付不重跑；宿主审查任务不能再生成整套审查或递归修复。

删除了 `team-followthrough` 内部单独检查历史通过标记、按结束时间挑选最终文件的旧结算逻辑。TUI、模型插件未加入第二份业务判断，未新增队列或执行器。

## 兼容与限制

- 计划存储仍为 v2、执行台账仍为原格式；没有给旧格式写入新的字段含义。`purpose`/`subject` 在准入后剥离，历史已存执行计划不必重写。新引用式提案必须带任务类型；旧文字式协议仅在已有兼容适配器转换为交付，不按名字猜测历史任务类别。
- 审查键使用 `audit-v2-` 命名空间，规则身份为 `emergence-assurance-v2`。旧审查记录原样保留可读，不把旧结论改写成新规则结论；旧版本证据不满足新自动验收门槛。需要时由原入口请求当前规则核验，仍受既有次数/权限限制；旧目标已经完成的状态不会自行复活。
- 没有改写旧证据来满足新规则，也没有升级磁盘结构，因此不存在破坏式数据迁移。回退代码不能把新核验记录当成旧程序已验收证据；回退前应停止运行并备份完整用户工作台、会话和执行台账，不能只替换部分记录。
- 类型约束和验收编号防止协议级混用，但不能证明模型对自然语言意图的每次分类都正确。通用命令对未追踪外部输入的影响仍不能凭空证明；本批核对宿主已记录的资源和交付。真实模型的计划质量与端到端成功率由 3E 固定构建矩阵检验。
- 本地回归通过不撤销首轮真实验收失败记录。下一批是 3D：时间、审批和失败恢复，之后才进行 3E 真实模型验收。
