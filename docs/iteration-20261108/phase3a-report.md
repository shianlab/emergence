# 3A：需求契约与计划准入

日期：2026-11-12。范围：第三阶段的 3A；不包含 3B 匹配策略、3C 收尾、3D 计时和 3E 真实模型矩阵验收。

## 问题与最终结构

此前把需求分析、旧计划、新计划的约束和验收文字用 Set 累加。模型换一种说法，条目就增加，GLM 跨项目样本最终触发 constraints 最多 12 项的限制。本批删除该累加路径，没有扩大条数上限或截断必需要求。

现在的数据流为：用户消息 → KIM 分析 → 宿主需求快照 → 引用式计划 → 唯一准入检查 → 原有分配与执行器。

- `core/domain/requirements.ts` 管理需求编号、来源、版本、延续修改和执行前完整性检查。原文保存在原会话消息中；快照保存消息引用、原文 SHA256、目标摘要。继续对话保留最初来源引用，版本由宿主分配。
- `core/domain/plan-proposal.ts` 定义模型可提交的工作图。`requirementRevision` 引用当前版本，每个步骤的 `requirementIds` 引用验收项；宿主继承约束、非目标及验收正文。全部验收必须被覆盖，每个步骤必须有验收。
- `core/adapters/plan-input.ts` 只做输入转换。新旧入口都进入同一个引用检查和计划物化流程；分配算法、任务队列、权限引擎没有另建一套。
- PlanningState 保存需求快照、步骤与需求编号绑定、物化后的计划。执行前再核对版本、对应关系和正文，不能在恢复或计划被修改后绕过检查。

## 修订、建议与预算

一次用户请求只建立一次需求分析。模型修订步骤、路径、依赖和实现方式时，需求编号与版本保持不变；修订次数照常累计，错误不能重置预算。

“继续”自动继承已有要求，即使模型省略约束也不会丢失。用户确实修改要求时，分析使用 `changes`，明确 add/replace/remove、需求编号、类型、正文、原因，并引用本轮新接纳的用户消息。旧消息、工具结果和计划建议不能充当本轮修改来源。首次分析仍直接从用户输入提取需求。

计划中的新增要求单列 `suggestions`，带来源和冲突编号；不会自动合并到已接纳要求。涉及新需求时进入待补充状态，不空转催促模型继续派工。普通实现选择放 reason/assumptions，无需逐条向用户确认。

来源和编号校验不等于能用程序完全判定自然语言含义；最初语义提取和用户修改含义仍由模型理解。需求记录也不授予工具权限，实际调用仍通过既有审批、路径、角色和继承限制。

需求快照、模型输入、绑定后的计划和每步任务上下文分别检查已有预算。超预算保留要求并指出问题，不截断要求以凑准入。工具参数从同一 Zod schema 生成；错误回执保留字段、原因和当前需求引用，便于有限修订。

## 兼容与回退

- 只有计划存储升级为 **v2**；配置、任务日志、长期记忆没有借机迁移。
- v1 读取只做内存转换，保留原文件。旧 ready 状态转为 blocked，重新接纳用户任务并建立需求后才能派发；已存在的执行任务仍由原任务日志管理，不重新创建。
- 首次覆盖 v1 前，在同目录写入字节一致的 `<scope>.json.v1.bak`。备份失败、已有备份不匹配、损坏、未来版本、错误 scope 或链接路径都拒绝覆盖。写入使用既有租约与原子替换。
- `work_json` / `plan_json` 保留为旧输入转换入口。已有需求时，总目标、约束和验收必须一致，步骤验收必须映射到已接纳要求；不能静默丢弃或合并改写后的文字。模型正常入口使用新对象结构。
- 回退代码基线为 `b124fc1`。旧程序不能直接读取 v2；先关闭程序并保留新数据，再按需恢复相应 v1 备份。新建 v2 计划没有 v1 备份，只能重新规划；不能将本说明当作任务日志回滚或历史副作用重放授权。
