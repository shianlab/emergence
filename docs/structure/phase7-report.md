## 本轮发现和修正

在线 core-live 验收脚本存在两处口径问题，未改动产品执行逻辑：

1. 将测试配置缩为单一模型时，仍保留日常窗口对其他模型的默认引用，触发配置校验。现在隔离配置同时清空窗口分配，保留实际配置不动。
2. 原断言把任何历史工具失败都视为最终链路失败。实际两个模型先尝试 write，被 KIM 的强制分析要求阻止，随后自行调用 emergence_analyze 并成功 write/read。现在仅接受一次、发生在分析之前且随后有成功分析和文件回执的明确拦截；未知错误、重复失败、未恢复拦截或缺失真实读写仍失败。新增四个反例/行为测试，并记录恢复次数，不能隐藏失败历史。

这说明核心约束实际进入工具执行路径，但不说明模型首次选工具已达到理想状态：两条线路仍各发生一次自动纠正。没有通过提示用户手动调用 KIM 或关闭核心来换取测试通过。

五分钟稳定性首次检查发现输入 P95 为 176.1934 ms，超过原有 150 ms 门槛；功能错误、内存和资源释放检查通过。CPU 采样定位到每次界面刷新反复枚举 Windows 环境变量进行脱敏。修正为一次同步呈现共用凭据快照，通过明确参数传递；不建立跨事件缓存，独立错误诊断仍实时读取密钥。新增轮换、标题/底栏及控制字符脱敏回归。失败记录和采样保留，性能门槛及测量方法不变，最终复测结果见下表。

## 结构复审

| 领域 | 当前维护结论 |
| --- | --- |
| Harness | 保持唯一 Agent 执行循环和会话历史；应用没有另造一套消息循环 |
| 窗口 | 独立项目/模型/会话；退役主控与跨窗口控制不在生产初始化路径 |
| 任务与持久化 | TaskEngine 组织本会话任务，TaskLifecycle 写状态，ExecutionJournal 保存执行与副作用事实 |
| 历史兼容 | task-history 在存储边界解码旧数据并保留 history；读取旧协调目标不重建调度器 |
| 会话与权限 | SessionLifecycle、SessionPermissions 和唯一 InteractionQueue 分工；异步切换与审批继续核对身份 |
| 规划/KIM | PlanningRequests 拥有状态，规划准入、规则与展示分别处理；核心拦截已有真实线路证据 |
| Code/Data | 通过能力契约接入，无 core → app 或具体 Controller 的反向依赖；Python 与工具执行边界保持 |
| TUI/配置 | UI 读取投影，挂载入口收尾；ModelDraft 隔离编辑数据，Connection 管理连接生命周期 |
| 规范 | 四种语言纳入同一检查入口；第三方与生成资产有明确范围，未新增宽泛豁免 |

两组内部类型耦合和较长的工作台组装函数仍存在，作为维护成本如实保留，不因验收通过宣称“没有技术债”。前六阶段的文件退出、接口迁移及状态责任详见各阶段迁移清单；测试数量变化有历史去向，不用删除当前行为断言获得通过。
