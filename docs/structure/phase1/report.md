## 完成结果

1. 选定当前项目根为唯一日常开发目录，在保留全部开工前改动的基础上创建 `codex/structure-phase1`。公开 1.00 提交的 601 个文件与开工前内容逐字节一致；旧本地 Git 历史不等于公开版本，后续同步须按 [基线说明](baseline.md) 处理。
2. 沿用既有架构巡检脚本，补充类型依赖、强连通组、计算型导入及动态注册位置。没有另建第二套检查入口。
3. 建立 [157 个源文件清单](module-inventory.json)、14 组模块职责、18 类关键状态归属与动态连接/资源收尾表，见 [职责与依赖](architecture.md)。
4. 建立 [15 组退役与兼容处理项](retirement.md)，区分当前能力、共享执行、历史读取与专属退役行为。
5. 建立 [20 项行为与验证入口](acceptance.md)，包含独立窗口、KIM、单会话执行、审批、Code/Data、外部能力、原生配置、恢复、安全与安装链路。
6. 添加当前维护入口，更新贡献说明和项目指引；旧主控维护、旧运行身份/编排报告及旧架构快照明确标为历史。

## 结构发现与后续归属

| 发现 | 实施阶段 |
| --- | --- |
| 值导入图无循环，包含类型的图存在 2 个循环组，其中一个涉及 33 个模块 | 第二阶段处理实际接口和依赖方向；不能把“运行时无循环”解释为结构已经干净 |
| Code/Data → app 共 8 条边，其中 3 条引用 Controller 类型、5 条引用通用文件工具；核心另有 1 条引用具体 CodeWorkHarness 类型 | 第二阶段按用途定义最小契约，下沉通用文件职责，同步迁移调用 |
| TeamCoordinator、TeamFollowthrough 与本窗口计划/调度/环境投影仍有连接 | 第三阶段分离共享执行与兼容读取，再解除生产构造并删除专属退役代码 |
| Controller、规划服务、TUI 闭包与原生配置代码职责集中 | 第四、五阶段依据状态归属整理；本阶段不机械拆文件 |
| Python/C# 内部关系及事件收尾无法由 TS 静态图完整证明 | 第六阶段统一适配现有构建的检查；第七阶段完成多语言、资源与实际交互验收 |

这些是已记录、尚待实施的结构整改项。本阶段没有声称解决全部技术债，也没有将现存问题写成检查豁免。
