## 产品目标与第一版范围

涌现是以 DeepSeek Harness 为首个执行后端的独立终端工作台。安装后输入 `emergence` 即可启动，默认使用当前目录，也支持 `emergence <项目路径>`。

第一版覆盖以下完整使用路径：

1. 创建多个会话，在同一个终端里分屏操作。
2. 每个会话独立选择目录、模型和配置，支持同项目或不同项目、同模型或不同模型。
3. 独立模式中由用户逐个指挥；协作模式中由指定主控向参与会话派活，用户随时介入。
4. 使用 Harness 的工具、Skill、MCP、会话与子代理等能力；以逐项核验的能力清单界定实际覆盖范围。
5. 保存会话记录、布局及偏好；在 Windows 终端中具备可靠的输入、显示和退出行为。

第一版优先原生 Windows + PowerShell，建议验证 Windows Terminal 和 VS Code 集成终端。macOS/Linux 的兼容结构从开始保留，实际支持声明以测试结果为准。

同一 Harness 下接入多个模型属于核心范围；接入 Codex、Claude Code 等完整 Agent 后端作为后续独立扩展。远程控制、关闭终端后持续执行的后台服务、完整终端模拟器不列入首版必交付范围。

## 总体分工与约定

采用 TypeScript 为首选应用语言，保留独立的启动入口、配置目录和产品身份。渲染器与 Harness 接入方式由第一阶段验证后确定。

| 模块 | 负责内容 |
| --- | --- |
| 命令入口 | 当前目录/指定路径启动、版本与帮助、退出状态 |
| 工作台 | 布局、焦点、窗格、通知、快捷键与模式切换 |
| 会话管理 | 会话身份、模型配置、有效目录、历史与运行生命周期 |
| 后端适配 | Harness 事件、工具执行、审批、问卷、取消、扩展与能力查询 |
| 协作调度 | 主控/执行者角色、任务分配、队列、状态、结果与人工接管 |
| 持久化 | 布局、偏好和任务元数据；会话历史优先由 Harness 持有 |

窗格、会话、项目和任务使用独立身份。隐藏或移动窗格不停止会话。中止当前轮次、终止会话、隐藏窗格、退出应用分别定义行为。任务状态来自执行回执与事件，不通过屏幕文字推断。

首版退出应用会停止其持有的运行时并保存可保存的状态；启动后恢复历史与布局，不自动重放可能产生重复副作用的未完成工具调用。进程恢复能力单独说明。

### 验收条件

- 两个会话可独立工作，取消 A 不会中断 B；事件与确认请求按会话准确归属。
- 中文输入、多行粘贴、缩放、焦点切换与退出恢复不存在阻断问题。
- 渲染器有实际对比记录；最终方案不依赖未经证实的 SDK 能力。
- 凭据或终端环境不足时，相关项目明确记录为待验证；模拟通过不代表真实模型或实机通过。关键缺口未解决时继续修复本阶段，其他独立准备工作可推进。

## 阶段三：多窗格独立工作版

**目标：实现用户分别指挥多个任务的核心体验。前置：阶段二的单会话流程稳定。**

### 工作清单

- [x] S3.1 实现布局树、左右/上下分屏、调整尺寸、切换焦点、最大化与窄屏折叠。
- [x] S3.2 每个窗格绑定独立会话，分别选择项目和模型；保留各自草稿、滚动位置和选区。编辑选区限本次运行，重启恢复草稿与滚动位置。
- [x] S3.3 管理多个活跃会话；隐藏窗格后继续执行，通过任务列表重新显示。
- [x] S3.4 按会话路由消息、审批、问卷、取消和错误；后台通知不抢走正在输入的焦点。
- [x] S3.5 保存布局与会话绑定，重启恢复；无效目录或无法恢复的会话有明确状态。
- [x] S3.6 实现共享目录的可见提示及已知修改冲突提示，提供可选 worktree 入口。提示不等于对所有外部工具实现文件锁。

### 验收场景

| 场景 | 必须观察到的行为 |
| --- | --- |
| 同项目、同模型 | 两份独立会话与输入，任务状态互不覆盖 |
| 同项目、不同模型 | 请求使用各自配置的路由 |
| 不同项目、同模型 | 文件和命令使用各自目录 |
| 不同项目、不同模型 | 目录和路由同时正确隔离 |
| A 工作、B 等待确认 | 用户能操作 C；确认只作用于 B |
| 关闭/隐藏某窗格 | 隐藏与停止有独立操作，其他任务继续 |

交付 **多窗格工作版**，重点验收 2 窗格和 4 窗格。更大数量受终端空间与机器资源约束，先不承诺无上限。

## 阶段四：主控协作版

**目标：主控能够真实派活、收结果，用户可以切回独立操作。前置：阶段三的多会话管理与路由通过。**

### 工作清单

- [x] S4.1 支持选择主控和参与者；切换模式保留现有会话与历史。
- [x] S4.2 定义任务记录，包含目标、发起者、执行会话、目录、依赖、状态和结果引用。
- [x] S4.3 让主控通过明确工具/API 派发任务；忙碌执行者接受排队，用户可看到队列并取消尚未开始的任务。
- [x] S4.4 处理进度、完成、失败、等待用户和依赖解除；对派发回执去重，避免重复执行。
- [x] S4.5 提供用户补充指令、停止派发、取消任务和接管会话的操作。停止派发与取消正在执行的任务分别处理。
- [x] S4.6 确定从协作切回独立模式时已派发任务的归属与通知；运行任务默认继续，新派发停止。
- [x] S4.7 协调共享项目中的修改；验证 worktree 隔离及成果整合流程，遇到冲突保持明确的待处理状态。整合需用户命令，不自动测试或解决冲突。

### 交付物与验收

交付 **协作体验版**。用“一个主控 + 两个执行者”完成可检查的小任务：主控派发两项工作，执行窗格实际运行并返回结果；制造一个失败和一个等待确认场景，主控不能将其误报为成功。用户接管、取消和切换模式不丢历史，也不重复派发。

跨项目协作允许目标不同，但成果合并不自动跨越项目边界。文件冲突和测试失败不能被主控摘要掩盖。

## 阶段推进与验证规则

- 六阶段按依赖推进；每阶段结束提供运行方法、可演示成果、验证结果和遗留问题。
- 文档、界面草图和模拟事件可支持设计判断；真实模型、真实工具与终端操作分别记录证据，不能互相替代。
- 对并发路由、取消、审批、队列、重复派发和恢复等高影响行为做自动化回归；视觉与终端行为补充实机演练。
- 不因阶段编号而把基础兼容和错误处理推迟：Windows、中文和退出恢复从阶段一开始持续验证。
- 持续维护本方案的完成状态和验证记录；未经验证的项保持待办。
- 常规实现选择按既定目标推进。只有影响产品范围、使用习惯或实际需要用户输入的事项，再集中说明并讨论。
