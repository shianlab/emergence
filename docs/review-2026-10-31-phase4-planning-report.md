# 下一阶段：GLM 主控规划超时专项

2026-10-31。承接第三阶段留下的主控规划失败，范围是任务入口、规划上下文和工具呈现；未修改用户模型配置、180 秒规划预算、8192 输出上限、权限策略或独立验收要求。

## 发现与修复

1. **首轮视图落后于工具状态。** Harness 先领取消息、解析工具和组装上下文，再执行 pre-step 准入。原工具激活会预览已领取的新消息，规划上下文却使用尚未更新的旧状态。现在上下文也预览已领取输入，主控首轮即获得自动规划流程；执行窗口首轮直接进入任务契约。预览不写入状态、不提前授权，新任务不会误用上一任务的方案。
2. **三条竞争的派工路线。** 自动主控同时收到直接 dispatch、完整绑定 plan/execute_plan、宿主分配 plan_work 的指引。现在自动主控只暴露工作分解入口，宿主负责窗口/模型匹配与后续验收；提交回执也明确指向同一路径。旧手动计划接口保留在手动宿主环境，CLI 手动操作不变；回归继续检查过期绑定和权限变化不能绕过门禁。
3. **重复、波动的上下文。** 窗口权限快照、角色全文和预算时钟被反复塞入团队与身份信息。模型现在得到窗口/角色摘要及稳定身份；完整资料仍由团队工具、运行身份查询、原工具回执和持久计划提供。约束与验收没有从任务契约删除。规划摘要有显示预算，超出时明确指向完整记录，不修改原始状态。
4. **可重复的实测。** 实测脚本新增显式的 planning-only 模式、规划耗时和前后构建哈希检查。该模式在两个项目都出现真实持久任务后结束，不把派发算作任务验收完成，也不硬性要求模型只能拆成两个步骤。
5. **计划纠错反馈不足。** 后续复测捕获了额外 `ready` 字段和不存在的 `shell:pwsh` 能力 ID。旧报错只说缺少能力，模型随后查询两份约 5 万字符的清单，耗尽剩余规划时间。现在接口明确状态由宿主计算、命令工具使用真实的 `tool:` ID；分配器拒绝缺失能力时列出具体 ID，并在同名实际能力存在时提供准确登记名。仍严格拒绝错误计划，不自动替换 ID、不改变权限。回归验证错误能力和模型声明的 ready 都不能进入任务队列。

生产改动集中在 `core/adapters/planning.ts`、`core/application/coordinator-context.ts`、`core/application/work-allocation.ts`、`app/collaboration.ts`、`app/runtime-identity.ts`。格式检查覆盖扩展到本轮修改的相关代码和测试，共 24 个文件。没有修改第三方 Harness 源码、另建队列、全局禁用外部 Skill 或取消安全检查。

两例精简上下文测试并行运行，每例前后哈希一致；它们刻意在派发后退出，工作窗口随后中断属于测试结束行为，未计为验收成功。完整闭环是在第一轮修复构建上完成的；之后进一步精简上下文、完成格式化，又补充计划纠错反馈。不同构建的成功不能混成最终版本全流程验收。格式化后复测失败也完整保留，没有通过反复重跑删除失败样本。

失败复测中，首轮模型回复耗时 117.380 秒，回执输出 6380 tokens；分析与三次读取均完成。约 151 秒首次提交计划因额外 ready 字段被拒绝，约 169 秒修订因 shell:pwsh 未登记被拒绝。随后两次能力查询完成，180 秒看门狗按预期取消剩余模型请求。没有派发成功却丢失任务的证据；此次失败由慢响应与接口纠错回合叠加导致。

交付构建测试前后 SHA256 与本机 dist 文件一致，首轮响应 57.050 秒。第一次计划遗漏必填 unknowns 数组，严格校验拒绝后，模型补齐再提交，通过正常门禁完成派发。该样本说明无效计划可以在预算内修订，但不代表模型从不出错。该测试没有运行到两个执行窗口的产物验收，因此最终构建的完整在线闭环仍未重新验收；已有完整在线闭环来自上表第一轮修复构建，最终源码由完整本地回归覆盖。

同一任务首轮运行上下文由 13627 字符降至 3806 字符，约减少 72%。模型工具声明由 49 项降至 46 项，移除的是自动主控的三条旧执行入口，不是删掉整个能力层。第一条模型回复仍有明显波动；这些小样本证明原故障场景现在可以通过，不证明任意复杂任务或任何网络状态都不会超时。
