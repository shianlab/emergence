# Emergence 结构整理方案

状态：第一至第六阶段已完成，见 [第一阶段报告](structure/phase1/report.md)、[第二阶段报告](structure/phase2-report.md)、[第三阶段报告](structure/phase3-report.md)、[第四阶段报告](structure/phase4-report.md)、[第五阶段报告](structure/phase5-report.md) 与 [第六阶段报告](structure/phase6-report.md)。[第七阶段](structure/phase7-report.md)的结构复审和自动验收已完成，本地候选为 1.0.1-rc.1；原生配置窗口手动验收待确认，尚未标记全部验收完成，也未发布。

本轮目标：在保持当前产品行为的基础上，明确模块职责、状态归属和依赖方向，降低修改、测试与排障的成本。以已发布的 Emergence 1.00（程序版本 1.0.0）为行为参考；本方案不直接改动发行物。

## 一、范围与完成标准

保留独立多窗口、现有 TUI 视觉和操作、模型配置、KIM 自动需求理解与规划、单会话任务执行、Code/Data 能力、Skills、MCP、记忆、权限、取消、恢复和持久化。

已取消的主控窗口、跨窗口派活和跨窗口控制继续保持退役。旧记录的读取兼容与当前执行能力分别处理，不因读取历史数据恢复旧功能。

整理后的代码需要满足：

1. 每类状态有明确的修改责任方；界面读取投影，通过明确操作请求变更。
2. 每条业务规则有唯一权威实现；临时转接的目的、移除阶段和调用方清楚可查。
3. Code/Data 与业务流程可以脱离具体 TUI 控制器测试。
4. 已退役的跨窗口控制逻辑退出生产依赖和初始化路径。
5. 新模块接管职责后，同批迁移调用方并删除被替代的实现。
6. 原有用户行为、安全边界和持久化兼容具有可追溯的验收证据。

不以文件变短、文件数量增多或测试数量增加作为完成标准。不引入第二套执行循环、任务库、重试队列或通用事件总线。

## 三、七个实施阶段

### 第一阶段：固定基线，明确职责与状态归属

**目的：确定哪些能力必须保留、哪些代码可以退出，以及每个模块应负责什么。**

工作内容：

- 核对公开仓库、当前开发目录与 1.00 标签的源码差异，选定唯一开发分支及工作目录；保留现有未提交改动，不直接覆盖目录或推送旧开发历史。
- 生成静态依赖图，分别检查运行时和类型依赖；补读动态注册、事件监听、资源释放及持久化调用。
- 建立状态归属表：窗口布局/草稿、会话生命周期、审批、规划、任务状态、执行回执、代码检查、数据作业、模型配置分别记录写入入口和读取方。
- 将现有模块和相关测试分类为“当前生产能力”“共享执行能力”“历史读取兼容”“仅服务退役功能”，每项标明实际调用或数据依据。
- 建立行为验收清单，覆盖独立窗口、KIM、工具执行、审批、Code/Data、Skills/MCP、历史恢复及模型配置。
- 将旧主控维护文档标为历史，明确当前维护入口，避免后续开发按旧需求重新接入协同功能。

交付：模块职责表、状态归属表、退役清单、依赖图、行为与测试对应表，以及可追溯的源码基线。

**完成条件：**没有归属不明的关键状态；每个拟删除模块都有调用及数据兼容结论；每项必须保留的行为都有验证入口。最近的验证证据只有在源码与运行环境条件匹配时才能复用，差异另做验证。

### 第二阶段：理顺模块依赖，建立明确接口

**目的：让业务能力依赖所需的最小接口，降低对具体界面和控制器的依赖。**

工作内容：

- 将 Code/Data 对 `SessionController` 的依赖改为按实际用途定义的接口，由应用组装层注入实现。
- 将核心端口中的 `CodeWorkHarness` 等具体实现依赖改为行为契约；避免用一个包含所有服务的大接口替代原控制器。
- 从 `app/instruction-files.ts` 分离被多个能力使用的路径、哈希、有界文件读取等职责。纯计算与文件 IO 分开安置，复用既有实现，不创建杂项 `utils` 容器。
- 规定依赖方向：业务规则保持纯净；应用流程依赖契约；适配器连接 Harness、文件系统与外部服务；TUI 和应用入口负责组装与呈现。
- 扩展架构检查至能力模块及类型依赖；明确适配层允许的连接，阻止未经声明的反向依赖和循环。

交付：实际使用的接口、调整后的导入关系、集中且职责明确的基础工具、对应架构检查。

**完成条件：**Code/Data 业务模块不再依赖具体 TUI 控制器；核心不通过具体能力类间接耦合应用层；同一工具只有一份实现；无为了通过检查新增的宽泛豁免。路径大小写、Windows 短路径、符号链接边界及结构化执行数据保持原正确行为。

### 第三阶段：剥离退役协同功能，保留单会话执行引擎

**目的：让当前产品的核心模型与“独立窗口”一致。**

工作内容：

- 按第一阶段清单，保留单会话准入、任务状态、预算、执行回执、取消、持久化与恢复能力，逐项切断它们对窗口角色和跨窗分配的依赖。
- 从生产初始化路径移除退役的 TeamCoordinator/主控持续协调逻辑；调整工作台、端口、工具注册及界面投影中的旧概念。
- 根据最终职责统一命名，名称变更与调用方迁移同步完成，不长期保留多组含义相同的入口。
- 历史数据通过边界上的兼容读取处理：保留记录及未知副作用事实，不自动恢复旧协同任务，不把未完成状态解释为成功，不清空用户数据库。
- 将仍覆盖共享执行能力的历史测试迁移为当前引擎测试；纯退役控制测试及运行宿主按清单退出活动测试依赖，必要的数据样本保留用于兼容验证。
- 清理相关失效配置、文档和命令说明；旧配置字段在读取边界按明确兼容规则处理，现有模型、密钥和历史保留。

交付：面向单会话职责的执行引擎、边界明确的历史读取模块、实际删除清单和测试迁移记录。

**完成条件：**生产运行无需构造旧跨窗口协调器；多窗口仅分别执行各自任务；KIM 与单会话执行能力继续工作；历史记录不会重启退役功能；被替代代码在生产依赖图中不可达，并从相应源码路径移除。

### 第四阶段：整理会话控制和规划核心

**目的：减少核心大类的职责及共享可变状态。**

工作内容：

- 将 `controller.ts` 的会话启动/切换/关闭、Harness 事件订阅、审批与授权、显示投影按实际状态归属拆开；控制器保留应用组装与对外协调职责。
- 将 `planning-service.ts` 的需求与规划状态、能力清单、计划准入、上下文投影、预算与停止处理按内聚职责拆开。
- 保留唯一权威状态，提取的模块通过明确操作协作；避免每个模块持有一份可变计划副本，或继续传入整个宿主对象访问所有内部成员。
- 明确异步操作、监听器、定时器和错误的收尾责任，确保切换、取消、超时、关闭时只有一条有效处理路径。
- 优先复用已有的生命周期、草稿、诊断与存储模块，合并职责重叠的封装。

交付：精简后的会话/规划入口、职责明确的模块、状态操作接口和资源生命周期说明。

**完成条件：**主要业务模块可独立测试；无法绕过规定入口修改任务/审批状态；旧控制器和规划服务不保留同一职责的第二套实现；拒绝、取消、超时、重启及副作用未知的语义不变。

### 第五阶段：整理 TUI 和原生配置界面

**目的：让交互、呈现与业务操作分工清楚，同时保持已确认的视觉和操作习惯。**

工作内容：

- 将 `workspace-ui.ts` 按窗口视图、输入与命令、导航与菜单、快捷键路由、布局与刷新、生命周期释放等职责整理；优先接入已有组件。
- 明确各组件拥有的临时 UI 状态，通过只读数据和明确回调连接；移除大闭包共享状态和重复分支，避免搬文件后继续共享所有变量。
- 将原生配置工具中的连接/进程生命周期、页面渲染、编辑草稿、校验与保存分开；展开难读的单行异步回调，使用表达业务含义的名称。
- C# 如拆成多个文件，同步调整构建源文件发现、输入指纹和打包，防止漏编译或复用错误的旧二进制。
- 保留 Windows Forms 原生控件、当前 .NET 运行目标、DPAPI 和模型分配协议；保持黑白灰 TUI、首页/对话页流程及现有中文交互。

交付：职责清楚的 TUI 组件与输入路由、可维护的原生配置工具、同步后的构建规则。

**完成条件：**首页、首次提交、消息/工具展开、中文斜杠推荐、快捷键、审批、焦点、分屏/关闭、窄屏与状态刷新通过交互验证；模型新增/修改/删除、密钥轮换、连接测试及退出保留原行为；重复打开/关闭不遗留监听器或后台进程。

### 第六阶段：统一代码规范和自动检查

**目的：让后续修改持续遵守同一套规则。相关约束在前面阶段随改动接入，此阶段统一收口。**

工作内容：

- 完善 TS 的命名、导入、异步错误处理和类型使用约定；继续沿用严格类型、格式及状态写入检查。
- 为自有 C#、Python 和必要的 PowerShell 脚本建立适配现有构建链的格式/静态检查入口。具体工具和版本在实施时验证兼容性并锁定，只增加开发检查需要的依赖。
- 纯格式修改单独提交，行为调整另行提交，使差异可以逐项审查。
- 第三方、生成文件和导入资产按精确清单排除格式改写，继续验证来源及完整性。
- 对大函数、复杂条件和重复逻辑建立审查规则；不以行数指标诱导机械拆文件，不用全局忽略掩盖现有问题。
- 统一当前维护文档、脚本命名和检查入口；文档与测试明确当前产品范围，历史材料有清楚标记。

交付：统一编码规范、锁定的检查配置、CI 检查入口和更新后的维护文档。

**完成条件：**干净开发环境可以执行同一组检查；已整理模块无未解释的检查违规；自有代码的排版与静态规范进入自动流程；开发检查不增加终端用户运行所需的 SDK 或服务。

### 第七阶段：完整回归、结构复审与交付

**目的：同时证明功能保持和结构改善。**

工作内容：

- 对固定源码版本运行完整类型、格式、架构、单元/Harness 集成和当前完整巡检矩阵；保留失败原因及修复后的复测证据。
- 验证真实终端和原生配置工具；检查多窗口独立性、取消/审批/恢复、Code/Data、Skills/MCP、模型协议及资源释放。
- 对旧版本配置、历史、任务日志和密钥做兼容验证，使用隔离副本，避免以测试修改日常用户数据。
- 再做依赖与密钥扫描，复核路径、权限、数据处理和执行边界；本地协议测试与在线服务测试分别记录，不能互相冒充。
- 单独进行稳定性检查，避免与构建争用资源混淆结果；与可比较的原基线核对响应和内存表现，不临时放宽失败阈值。
- 从干净检出构建候选包，验证安装、升级、回退和卸载。已发布的 1.00 标签及发行物保持不变，候选包采用新的版本标识。
- 对比前后依赖图、状态归属、重复实现、旧逻辑清单和典型改动路径，形成最终结构审查报告。

交付：完整验收报告、前后结构对照、剩余问题清单、新版候选包及变更说明。发布作为后续明确操作，不在本方案编写时执行。

**完成条件：**没有未解释的测试失败或高风险缺陷；不存在生产仍依赖退役协调器、旧新实现并存、状态归属不明、为通过检查而扩大豁免等未完成事项。全部保留能力均有验证记录，已移除的能力及实现有完整去向。

## 四、每阶段的工作方式

1. 固定本阶段源码基线，检查已有改动，确认范围和行为契约。
2. 按一个完整职责迁移：接口、实现、调用方、状态、资源释放一起处理。
3. 删除被替代的旧实现，更新相关文档与必要的行为/边界回归。
4. 运行本阶段受影响的验证；修改核心执行、审批或 TUI 时执行相应完整检查。
5. 审查最终依赖和调用链，报告完成结果、旧代码去向、验证证据和剩余问题。

同一阶段内部使用可审查、可回退的小提交；不以增加第二套系统达到表面上的“模块化”。Git 提交可以回退，用户数据不依赖删除或强制降级来回退。

任何阶段出现回归，先在该阶段修复并验收，再进入下一阶段。测试数量允许随退役/迁移合理变化，但必须记录去向，保留当前能力与安全边界覆盖；不得通过删断言、无理由跳过或修改成功定义制造通过。

阶段报告统一回答五个问题：

- 本阶段哪个职责的归属变清楚了？
- 哪些旧代码已删除或隔离，其生产调用是否已经清零？
- 哪些调用方和数据兼容路径受影响？
- 哪些测试/实际操作证明行为保持？
- 是否仍有待移除的转接层或未解决问题？

## 五、推进顺序

第一阶段固定基线与职责 → 第二阶段理顺依赖 → 第三阶段剥离退役协同 → 第四阶段整理会话与规划 → 第五阶段整理界面 → 第六阶段统一规范 → 第七阶段完整验收。

第一阶段以当前源码事实细化模块切分和测试对应关系，不重新发明一套路线。后续如需调整某个模块的归属，在阶段记录中说明依据；不得默默扩大功能范围或重新引入已取消的跨窗口控制。
