# Code / Data 增强第三阶段交付报告

日期：2026-10-30。范围：编程修改、检查反馈、版本保护、恢复预览和 KIM 协作交付。第四阶段的数据接入与执行尚未开始。

## 已接入产品

编程任务现在沿用现有 KIM 目标分析、项目理解和工具权限，接入“复现 → 修改 → 检查 → 根据诊断修复 → 交付”。无需安装或点名 Skill，没有增加另一套 Agent 主循环或任务数据库。

新增两个原生工具，由 Agent 根据任务使用：

| 工具 | 行为 |
|---|---|
| `emergence_code_work` | `begin` 建立任务基线；`checks/status` 提供项目检查命令及实际结果；`preview` 查看单文件修改前后、差异位置和恢复条件 |
| `emergence_code_restore` | 使用预览的内容 hash 和文件系统版本恢复一个已记录的既有文本文件；仍受编辑权限、项目指引及沙箱约束 |

用户仍可直接说“这个函数算错了，修复并验证”。原有工具的执行状态反馈继续显示；没有变更已定稿的 TUI 视觉和模型配置插件。

## 修改与验证如何串起来

- 从 package.json 发现实际存在的 `typecheck/lint/test/check`，识别 npm、pnpm、yarn 及包目录。Python 从 pyproject.toml / pytest.ini 中发现 pytest、Ruff、mypy 配置线索。只产生候选，不安装依赖、不直接执行项目脚本。
- 项目检查仍通过普通 `pwsh/bash` 工具运行。只绑定与候选精确匹配的命令，允许根目录 `npm test` 别名；额外拼接命令、任意 Shell 调用不冒充该检查。
- 修改前后记录文件版本；检查记录命令、callId、源文件 hash、基线/修改后阶段、退出码、失败/取消/后台状态、输出摘要和路径/行列诊断。
- 类型诊断支持常见 tsc、ESLint unix、pytest/Ruff 路径格式；不认识的输出保留摘要，不编造位置。
- 检查期间源码变化、结果过期、未运行、超时、取消、只有后台启动，以及已知的“没有运行测试”输出，都不能记成验证通过。相同版本、同一检查连续失败两次会阻止无效重跑。
- 测试或检查配置发生变化时，标记口径变化、要求独立审查，不能把降低标准后的绿色结果直接当成原问题已解决。
- 项目源码观察仍有文件数/大小预算。`verified` 只表达当前已发现检查在当前受观察版本上成功，不代表全部业务行为、外部服务或未扫描依赖都已验证。

## 版本保护与恢复

实际活动文件工具链使用上游 `dsh-fs-observation-policy` 和 `replaceIfVersion`。读后发生的外部修改会被拒绝覆盖；原生 literal edit 默认拒绝不唯一匹配。新增记录层不替代这些保护。

变更记录保存修改前的真实文本，包括已有未提交内容和 CRLF；恢复先提供范围与差异预览，再核对预览 hash，并用文件系统提供的版本做条件写入。不执行 Git reset/stash，不删除新增文件，不承诺撤销任意 Shell、网络、数据库或其他未记录副作用。多文件恢复逐文件核对，不声称跨文件事务性回滚。

当前每个运行最多记录 12 个源文件、64 次检查；源码单文件上限沿用第二阶段 256 KiB。记录位于用户 Emergence home 的 `core/code-runs/`，按会话、任务和项目隔离；新运行保留旧记录归档。重启可以恢复变更记录，但历史成功检查不会自动成为当前成功证据，需重新运行。异常结束后的不确定修改不自动恢复。

已确认新目录中的文件创建兼容原工具；已获授权的项目外编辑继续走原工具权限，不纳入当前项目变更集。

## 多窗口与独立验收

主控仍通过现有 KIM 计划、任务调度、权限继承和独立审查/验证派工。执行结果增加可选的代码摘要：运行 ID、文件路径、检查编号、命令、版本、退出状态及口径变化。依赖任务可以获得该摘要；历史任务数据无需迁移。

失败复现回执不删除。仅当同一检查以未降低的测试口径、当前源码版本重新成功时，才将相应非零检查标记为已修复；其他工具错误、取消、未知副作用和不同命令失败仍然保留。缺少当前验证的代码修改不能靠一句成功报告完成验收。

同一执行窗口的后续任务不继承前一个任务的变更集。检查输入较小时，实际源码版本也进入原有执行 manifest；完整的有界输入清单保存在代码运行记录。超出 manifest 32 项上限时不截取后冒充完整输入。
