# 主窗口自主编排方案

状态：第一至第四阶段均已实施并巡检（2026-10-30）。记录见 [第一阶段](master-phase1-report.md)、[第二阶段](master-phase2-report.md)、[第三阶段](master-phase3-report.md)、[第四阶段](master-phase4-report.md)。第四阶段通过真实 DeepSeek / GLM 双模型、双项目完整验收；后续按实际使用反馈调试，不自动新增阶段。

## 目标与用户操作

用户打开两个或更多窗口，右键将其中一个设为主窗口，然后向主窗口描述总任务。主窗口默认承担理解需求、拆解、选择执行窗口、派发、跟进、审查、有限修复和汇总的责任，不要求用户逐步输入派工命令。

没有主窗口时，各窗口继续独立工作。设为主窗口后，空闲且允许参与协作的窗口自动进入团队；用户正在独立操作或已接管的窗口不抢占。新增窗口更新团队清单；不同项目可以参与，但任务必须绑定正确目录，不自动把所有窗口切到同一项目。

并行由任务结构决定：可以独立执行的步骤并行，有依赖的步骤按序执行；简单问答无需制造任务。只有一个执行窗口时可以分批承担实施、研究或验证等职责，验证使用独立上下文，不能把同一实施者的自述当作验收。

## 现有基础与缺口

- `WorkspaceController.setMaster()` 已设置协作模式，新增窗口可自动加入；当前主要是加入 worker 列表，缺少明确的窗口角色偏好与能力画像。
- `CorePlanning` 已有需求分析、能力清单、计划校验和执行入口。角色库包含 planner/researcher/developer/reviewer/verifier；角色通常绑定到任务，还不是完整的窗口能力声明。
- `Collaboration.executePlan()` 已能把计划提交到持久队列；调度器支持依赖、权限、任务契约、作用域和恢复记录，继续复用。
- 已有 worker 回执唤醒主控、独立审查、验证和修复机制，不能把它描述成只能手动派工。但目前依赖模型主动调用多个工具，尚未形成每个总任务都必须收敛的协调流程。
- 本轮补齐主控运行策略，不另建调度器，不把 KIM 作为外部 Skill 触发条件，不用一句“你是主 Agent”的提示词代替程序控制。

## 第一阶段：主控职责与团队能力

交付：设为主窗口即启用协调职责，并建立可查询、随运行变化的团队清单。

窗口资料包含项目/会话/模型、默认或用户指定的角色偏好、可用工具/Skills/MCP、权限、当前任务、空闲/忙碌/接管/断开状态。区分“声明擅长”“当前可调用”“已有成功证据”，不凭模型品牌编造擅长领域；角色偏好不能越过权限。

默认角色为自动选择，用户可选“偏实现”“偏研究”“偏审查”等，但不强制配置才能使用。角色选择作为当前任务契约的一部分锁定；执行中修改偏好只影响后续任务。

收到新总任务后创建持久协调记录，关联原始用户请求、需求理解、团队快照、约束、验收和状态。仅有空闲窗口不产生新工作。设为主控不重放历史消息；已有未完成任务沿用既有记录，避免重复启动。恢复会话沿用当前暂停恢复约定，并提供清楚入口。

验收：两窗/三窗、不同项目/模型、动态开关窗口、用户接管时清单和身份正确；同一请求不会建立重复总任务。

## 第二阶段：需求拆解与自动派工

交付：用户只提交总目标，主控自主生成并提交可执行分工。

在真实任务入口启动协调步骤，模型产出结构化决定：直接回答、等待关键补充或提交任务图。宿主验证决定，不能仅输出一段“我将安排”就视为已派发。缺少必要分工或输出无效时有限纠正，超过预算显示具体阻塞原因，不静默结束或无限重试。

复用 KIM 原生需求理解，先明确目标、约束和验收，再拆成有依赖的子任务。每项含范围、目录、交付物、验收、角色和预算。候选匹配先过滤目录、权限、工具和接管状态，再考虑角色偏好、负载及实际证据；没有专业画像时按通用执行能力分配并说明依据。忙碌但可排队与不可分配要分别表示。

对可拆的大任务默认分配给合适 worker；主控保留统筹工作。如果只能由主控处理或没有合适 worker，记录原因和后续选择，不为占满窗口强行拆任务。

复用现有计划校验与执行队列，派发采用稳定请求标识防重复。共享文件写入冲突串行化；跨项目交付通过明确契约连接，不擅自变更工作目录。自动执行/自动编辑/审批/只读规划继续遵循现有权限；仅讨论不触发实施，常规分工不另加一层用户确认。

验收：不包含“派给窗口”“调用 KIM”等提示的自然大任务，自动出现真实任务记录并启动 worker。验证两个窗口能顺序完成，三个窗口能实际并行，重复回执不重复执行，讨论和独立模式不误启动。

## 第三阶段：自动跟进、审查和收尾

交付：主控在派活后继续负责到达验收条件，无需用户手动推动下一步。

协调记录明确区分理解、规划、派发、等待结果、审查、修复、完成、等待用户、暂停。由接受请求、任务回执、审查结果和窗口变化等真实事件驱动，合并重复唤醒；主控忙碌时排入待处理事件，不丢失通知、不启动两个竞争协调轮次。

前置任务通过验收后启动后续步骤。结果提交后自动进入已有独立审查/验证流程；缺陷在原授权目标内进行有限修复。故障后的重试或换人须先核对实际副作用，避免重复修改；没有可用窗口或存在结果不确定性时保留记录并明确阻塞。

总任务保存步数、重试和时长预算；有可靠 token 数据时记录用量，不虚报成本。达到预算后可见地暂停。只有缺失关键需求、权限审批、目标变更等需要用户决定的事项才询问，常规排队和进度由主控处理。

汇总须关联实际产物、验收证据和未完成项。queued、needs_review、等待用户、工具失败等不能被写成成功。用户打断、取消、接管和恢复保持有效，过期回执不能恢复已取消的工作。

验收：开发完成后自动审查；审查失败能有限修复并复验；断连、主控忙碌、窗口关闭、取消与重启恢复均不重复派工、不虚报完成。

## 第四阶段：中文可见反馈与整体验收

交付：用户能直接看懂主控正在协调什么，并能随时介入。

复用现有右键菜单、窗口身份、任务侧栏与状态区域，不重新设计主题。展示总任务、分工摘要、执行窗口当前职责、分配原因、依赖和实际进度，例如“正在理解目标”“已分配 2 项任务”“等待后端结果”“正在核对验收”。状态来自协调记录，不使用虚假进度。

提供点击暂停/继续、接管窗口、查看任务与必要审批入口，保留命令作为补充。不同项目、忙碌窗口和等待用户的原因可见。普通任务通知不占据聊天正文的大量空间。

建立两层证据：确定性集成测试覆盖状态、队列、权限、冲突、恢复和预算；实际配置模型测试覆盖自然语言任务的自主拆分、真实工具调用、产物和验收。真实测试在隔离项目运行，不能用模型说“已分配”作为证明。覆盖单个 worker、多 worker、不同目录、不同模型、失败修复、取消和无效计划等情形；结果注明实际测试的模型范围。

最终验收标准：用户只需设置主窗口并给出总目标，正常授权范围内从分工到核对汇总都能推进，无需再说“现在派活”“继续下一步”“检查一下结果”。

## 实施顺序与阶段边界

按第一至第四阶段推进，每阶段完成后巡检并报告。第二阶段形成可用的自动派工，第三阶段形成从派工到验收的完整流程，第四阶段完成可见交互和综合验证。当前不做安装包、发布或额外扩大多 Agent 架构。共享 UI 文件修改与另一页面协调，保留其最新改动。
