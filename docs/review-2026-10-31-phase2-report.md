# 巡检修复第二阶段：调度资源与超时生命周期

日期：2026-10-31。状态：完成，已构建本机版本。对应三阶段修复计划的第二阶段。

## 已完成

### 独立审查资源

- 自动审查先寻找同项目、匹配审查角色模型的独立空闲会话，支持复用从未承接任务的空白窗口，以及只做过同类审查的窗口。
- 实施会话、个人对话、另一类审查的会话、用户草稿、用户接管和已有排队任务的窗口均不会被当作空白资源使用。显式指定窗口也执行相同的独立性检查。
- 分配中预留窗口，计入正在创建的窗格，避免并发请求重复占用或突破 16 窗口上限。
- 临时资源忙碌时，主控显示等待原因并继续跟进；失败的资源申请不消耗成功协调动作预算。没有独立上下文且窗口已满时，明确要求释放窗口或建立空白会话，不关闭用户会话来腾位置，也不把实施者冒充审查者。

### 负载与队列

- 分配评分同时考虑已有排队数、正在执行的任务数和本图新增任务；角色偏好仍有效，但不再压过明显的积压。
- 任务显示实际等待原因：依赖完成、独立验收、窗口忙碌、用户接管、读写资源、并发额度或暂停。
- 对重叠资源保留先来任务的优先权，防止新到的读取持续抢占、让早先写入一直无法开始；依赖尚未满足或协调已暂停的任务不会错误地持有这项优先权。
- 只有宿主确认的文件只读任务可共享读取范围。写入仍互斥，未知工具/Shell 仍保守处理；只读并行任务调用写入或额外副作用工具会被拒绝。

### 计时与超时

- 新增共享的预算与计时模块 `src/core/domain/run-budget.ts`，分别累计执行、审批等待、排队和暂停时间；状态随既有任务/协调记录保存。
- 等待审批不再消耗执行额度；同一目标或同窗口里因审批而阻塞的排队任务，也不会继续消耗普通排队额度。
- 主控规划和派发任务都有主动检查定时器，持续无响应时可发送取消信号，不必等模型进入下一步。到时限刚好形成有效方案的既有处理仍经过正常权限门禁。
- 排队和审批等待有各自上限；整体历时包含暂停和等待，防止无限挂起。任务记录明确区分 execution、approval、queue、overall；总任务因预算失败标为受阻，不宣称完成，不盲目重试副作用。
- 进程恢复仍保持中断/暂停状态，需要原有恢复决策；不会因为保存了计时状态就自动重放任务。

配置位于现有配置的 `orchestration.budgets`，默认值如下（毫秒）：

```json
{
  "queueMs": 600000,
  "approvalMs": 1800000,
  "totalMs": 3600000,
  "planningMs": 180000
}
```

也就是排队 10 分钟、审批等待 30 分钟、整体历时 60 分钟、主控实际规划 3 分钟。执行任务沿用自己的 `maxDurationMs`，未提供契约的任务采用 10 分钟执行预算。配置解析有上下界检查，旧配置会补默认值。修改时合并对应字段，保留已有角色、模型和权限配置。

普通独立聊天继续使用模型适配器和工具自身的超时机制；本轮新增的主动规划/执行预算针对主控规划及派发任务。模型或工具的实际失败回执仍优先保留，不能用预算规则伪造成功。

修正了原 CodeWorkflow 模拟提供者的隔离方式：模型适配后的消息不保证携带内部 source 元数据，测试现在依据实际派发消息识别执行窗口，避免主控回执抢走执行窗口的固定脚本响应。生产模型调用逻辑未为适配测试而改变。

持续运行是本轮的 **65 秒短时回归**，不是五分钟或全天稳定性证明。原通用测试输出中有固定的 Five-minute 描述，实际时长以 configuredDurationMs/durationMs 为准。此轮使用受控模型响应与真实本机 Harness/文件/进程，不代表已重测付费模型的语义分工成功率。
