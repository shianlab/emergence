# Emergence 全面巡检与修复计划

日期：2026-10-31。范围：当前本机源码、已有构建、主控派工/执行/独立验收链路、权限与凭据、Code/Data 能力、模型配置和 TUI 主控交互。

本轮按“先检查，再出修复方案”执行，只新增诊断探针与报告，未修改生产逻辑。下面区分实际复现、静态设计缺口、历史记录及尚未验证的外部条件。现有测试通过，不等于复杂任务已经稳定。

## 结论与证据

### 1. 已复现：合法长上下文无法进入独立审查，且遗留窗口（高优先级）

位置：`emergence/src/core/application/assurance.ts:43`，尤其是窗口分配和随后调用 enqueue 的顺序。

原任务允许约 8000 字符上下文；审查任务直接把原上下文、治理说明、验收项和交付索引拼接进同一个限长字段。使用 7900 字符上下文的任务能正常执行，但发起独立验证时超过 8000 字符而被拒绝。拒绝前已经创建新窗口，任务没有创建，窗口却增加一个。

后果：任务做完后卡在验收；重试还可能继续消耗窗口。不应靠增加一次字符串上限解决，因为嵌套上下文和数据交付索引还会继续增长。

修复方向：统一执行/审查上下文构建及预算校验；原始约束和验收项作为有权限边界的持久引用传递，展示摘要与完整数据分开。先完成参数与容量校验，再预留执行资源，提交失败回收本次新增资源。禁止静默截断范围、验收和权限要求。

### 2. 已复现：窗口满额时自动审查忽略可用空闲窗口（高优先级）

位置：`emergence/src/core/application/assurance.ts:52`。

自动复用仅寻找“此前执行过同类审查、没有其他任务历史”的窗口；没有这类窗口就新建。复现中共有 16 个窗口，存在从未执行任务的独立空闲窗口，自动验证仍因窗口上限失败；显式指定其中一个空闲窗口则成功创建验证任务。

后果：多窗口、多模型或多项目场景更容易在验收阶段失败，与实施任务本身是否完成无关。

修复方向：统一执行窗口分配，选择经核验的独立上下文，区分空白会话、实施会话、review 会话和 verify 会话。不能仅凭“空闲”复用有污染的对话。临时资源不足进入有原因、有期限的等待；真正无合格资源才明确阻塞。保留实施、审查、验证之间的独立性。

### 3. 已复现行为：用户审批等待消耗执行预算（应调整的超时语义）

位置：`emergence/src/app/collaboration.ts:445`；总任务预算另见 `src/app/team-followthrough.ts:120`。

把任务执行预算设为合法的 1000ms，在第一次写入审批处不作回答：任务进入 waiting_user，随后以“任务运行时长预算已耗尽”取消，实际写入次数为 0。默认预算更长，但计时方式相同。总任务也先判断墙钟预算，再判断等待用户状态。

这不是权限绕过；审批保护正常。问题是“机器执行超时”与“用户尚未回答”混用。应分别记录排队、实际执行、等待审批及整体历时，等待审批暂停执行计时；整体历时仍有明确上限，不无限挂起。超时原因应区分规划、模型响应、工具执行、排队和审批等待。

### 4. 静态确认：分配偏好较粗，缺少已有队列负载（优化项）

位置：`emergence/src/core/application/work-allocation.ts:15`、`src/core/application/task-allocation.ts:6`。

当前有项目、能力、角色和权限门禁，不能说是随机派工。但排序中角色偏好加 100、空闲只加 10，负载只统计本次新图分配的任务，未计已有排队数量。任务的资源冲突也偏保守：不具备安全文件并行契约的任务按整个项目独占，重叠只读范围同样冲突。

这可能造成“有空窗口却仍排队”，但不代表所有串行都是 bug：Shell、外部工具或不明副作用必须保守。建议先增加队列深度、明确的等待原因与负载权重，再以宿主可信读写契约区分共享读取和互斥写入。不要依据模型或远端工具自称只读放宽权限。

### 5. 静态确认与已有测试：规划可提交，但扩展后无法派发

位置：`emergence/src/core/adapters/planning.ts:77`、`:168`；已有回归 `tests/master-dispatch.test.ts:170`。

提交时校验输入 JSON 长度；窗口、会话、绝对路径和分配理由补全后，还会在执行前再次检查总长度。因此存在输入合法、绑定后的计划超预算而不能执行的情形。当前会安全阻止执行，已有测试也覆盖了这种阻止；缺口在于准入阶段没有提前返回可修订的最终预算结果。

修复方向：提交阶段使用最终绑定结构做完整预检，统一准入结果；大任务可按有依赖关系的批次推进，不能直接删除预算或无限扩大上下文。保留执行前对实时权限、会话和产物版本的再次校验。

### 6. 本机历史记录支持“派发前中断”，但不等于当前版本新复现

只读取了保存状态中的状态、时间与计数，未导出用户完整任务或凭据。一条本机协调记录在北京时间 10:50:32 被标为 blocked，原因为“规划步数或时长预算已耗尽”，已有 2 项分配信息，实际执行任务数为 0。

该记录早于上一轮最终验收，不能把它算成当前版本新复现的同一 bug。当前已有“有效计划恰好到预算边界仍可派发”的修复及回归。仍需补充长输入、多任务、多轮修订、等待审批和真实流式响应组合测试，验证剩余边界。

规划的 180 秒检查发生在模型步骤边界；底层模型适配器另外有流空闲 watchdog，默认 300 秒。因此不能说系统完全没有超时，但规划限时、网络空闲限时和整个任务截止时间并不统一，也不能保证 180 秒时立即中止正在持续输出的模型请求。

## 代码结构判断

已有领域、应用、适配器和持久化分层，可以继续使用。问题集中在编排接缝和预算语义，而不是需要推倒 Harness。

`collaboration.ts` 约 590 行，同时承担准入、队列、生命周期、持久化协调及工具注册；`planning.ts` 约 403 行，也混有预算、模型钩子、分配及上下文构建。两者分别有 68、47 行超过 180 字符。长行只是可读性指标，不是 bug 数；但密集语句确实不利于检查状态变化顺序。项目有类型检查和测试，尚缺统一的格式化/静态规范执行入口。

整理原则：先固定回归，再按现有模块抽出上下文构建、预算策略、资源选择和生命周期转换；保留原调度队列、任务 ID、权限门禁及持久化来源。不新增第二套任务状态系统，不把所有问题堆进 TUI，不以整库格式化淹没功能改动。

## 建议按三个阶段实施

### 第一阶段：派工准入与上下文完整性

目标：任务提交后能明确知道是否可派出，长任务不会到验收才因字段溢出失败。

- 统一计划绑定、执行任务和审查任务的上下文构建与预算预检；约束/验收完整保存并按权限引用。
- 在状态进入可执行前返回最终结构的预算错误，让模型在有限次数内修订；明确拆分批次方式及依赖。
- 审查提交先校验后分配；失败事务只回收本次创建的资源，保留用户原窗口。
- 将长上下文诊断改成“合法任务完成审查且无窗口泄漏”的正式回归。

验收：7900 字符原上下文、较长文件路径、较多验收项、原生数据交付索引、12 步任务图都得到可执行计划或清晰且可修订的准入结果；不得显示 ready 后才因可提前判断的字段预算失败。取消/提交失败不残留半成品任务和窗口。

### 第二阶段：调度负载、审查资源与超时生命周期

目标：多窗口持续派工与验收能够闭环，等待和失败有准确归因。

- 为自动审查复用真正独立且合格的空闲上下文；容量不足等待或明确阻塞，不无条件开窗口。
- 负载纳入已有队列和运行任务；角色偏好可解释，避免长期饥饿。安全读写资源冲突逐步细化，未知副作用仍独占。
- 统一规划、排队、执行、审批等待、模型响应和总任务预算；以可注入时钟测试，保留持久化与重启语义。审批等待不扣机器执行额度，仍有独立等待/整体上限。
- 统一超时、取消、暂停、失败、待核对的状态转换；不把“生成分工”算成“已派发”，不自动重试不确定副作用。

验收：2/4/8/16 窗口、同/跨项目、不同模型、队列拥堵、审批延迟、暂停恢复、临时掉线和窗口满额；满额有合格空闲上下文仍能验收，无合格资源时给出原因；没有任务饿死、审批误取消、重复执行或假完成。

### 第三阶段：代码结构与安全回归、统一验收

目标：形成可维护的稳定版本，满足本机长期调试使用。

- 在前两阶段建立的测试下整理编排模块职责、状态原因类型及公共配置，去除重复预算与散落的魔法数；格式化仅覆盖相关模块，提供后续规范检查入口。
- 复查权限继承、审查独立性、目录边界、配置令牌、日志脱敏、MCP/Skills 和 Data 安全门禁，特别防止为提高派工成功率而放宽限制。
- 跑全部回归、TUI 交互、原生配置生命周期、故障恢复和多窗口持续运行；重跑 Code/Data 混合任务。
- 另用当前已配置模型跑固定的小规模真实任务集，分别记录分工适配、实际派发、产物正确性、独立验证、耗时和失败原因；确定性测试与真实模型结果分开报告，不用 mock 成功替代真实成功率。

验收：第一、二阶段所有缺陷回归转为正确行为；安全测试不退化；构建与运行版本一致；形成可复查的测试记录和剩余问题清单。仍以本机运行调试为交付，不打安装包、不上传 GitHub。

执行顺序：先完成第一阶段，再进入第二阶段，最后统一验收。每阶段交付实际改动、对应回归及剩余边界；本报告本身不代表上述修复已经实施。
