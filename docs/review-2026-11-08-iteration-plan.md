### 前三阶段共同目标：形成完整、统一的代码结构

这里的“完整”指：入口到执行、回执、恢复、展示之间有明确契约；每类状态有唯一负责人；新功能沿既有结构扩展；旧业务路径在迁移完成后退出；源码、测试、文档和运行资源相互对应。文件拆得更小、测试数量增加，都不能单独证明完成。当前已有可靠能力应迁入最终结构，不推倒重写，也不永久并存两套编排实现。

以下是目标职责边界，具体文件名在第一阶段结合调用关系确定，优先复用现有目录，不为凑层数建立空接口或新框架：

| 边界 | 负责 | 不负责 |
| --- | --- | --- |
| TUI / CLI / 原生配置入口 | 收集用户意图、提交命令、显示业务状态与审批 | 自行修改任务结果、推断完成、建立另一份队列 |
| 应用用例与 KIM 治理 | 意图分析、计划准入、任务生命周期、分配与恢复、验证/审查流程 | 直接绘制界面、依赖整个界面控制器、在多处重复权限规则 |
| 领域契约与规则 | 任务/能力/权限/回执结构，合法状态转换与完成条件 | 读取用户全局配置、访问文件系统、调用供应商 API |
| Harness、模型与工具适配 | 将模型建议和实际执行结果转换为统一契约，执行取消与权限检查 | 把模型自述当作完成凭证、绕过任务归属与审批 |
| 存储与系统适配 | 持久化、租约、原子写入、平台/进程能力 | 独立决定业务状态、损坏时静默返回空状态 |
| 组合入口 | 读取配置并装配上述组件及其生命周期 | 承载计划、派工和审查的业务规则 |

主链路为：用户请求 → KIM 分析与计划 → 准入及唯一任务队列 → 工具执行 → 实际回执 → 验证/审查 → 汇总与界面展示。简单任务可走短路径；独立窗口仍可独立工作。KIM 是应用核心治理环节，不改成可选 Skill，也不强迫每条消息启动多 Agent。

依赖方向要求：领域不依赖应用与界面；核心应用通过必要的小接口使用外部能力；适配器实现接口；组合入口连接它们。界面可以保留显示缓存，但不能成为业务状态权威。任务执行状态、租约归属、审批决定、产物版本分别明确唯一写入者及其一致性约束，不笼统地塞进一个全局对象。

需要明确的兼容范围：既有会话/任务持久化数据、配置 schema、插件调用接口和工具协议。第一阶段逐一决定“保持兼容 / 需要迁移 / 允许废弃”，并记录消费者、迁移方式和回退限制，不能默认删除旧文件就算完成。

**阶段门槛：** 核心链路和状态归属已查清；第二阶段每一批改动均有目标和退出条件；安全扫描后的候选提交不包含密钥、用户对话、原始审批数据、本机虚拟环境和冗余构建；核心代码、测试、品牌资产及上游声明保留。Git 仓库仅位于项目目录。作者许可证的最终选择可留到发布阶段，不阻塞内部重构。

### 第二阶段：完成架构重构与代码规范收口

**目标：把第一阶段的设计真正落实为一套运行代码。** 本阶段优先保持既有行为；第三阶段再集中改进协议和编排策略，便于区分“搬迁导致的回归”与“主动改变行为”。

按以下顺序实施，每批贯通实际调用链并完成回归后再推进：

| 子步骤 | 重构内容 | 旧逻辑退出条件 |
| --- | --- | --- |
| 2.1 契约与依赖方向 | 将核心使用的权限 schema、错误脱敏等移出 app 依赖；用必要的小接口替代对整个 WorkspaceController/SessionController 的依赖 | 目标核心模块不再反向导入 app；原位置仅在确有兼容消费者时暂留导出，不复制实现 |
| 2.2 任务生命周期与持久化 | 收拢准入、排队、执行归属、结算、取消及恢复的状态转换；提取经过测试的安全文件操作 | 所有写入者迁到指定入口；只保留一个调度队列；各存储 schema、锁、预算与恢复语义不被通用包装抹平 |
| 2.3 编排适配与回执闭环 | 拆解 Collaboration 中的工具注册、执行协调、证据采集、结果归档职责，保留明确调用关系 | 新路径接通真实 Harness 和存储；旧业务分支删除；若保留 Collaboration 外观，只负责组合/委托，不保留另一套规则 |
| 2.4 KIM 规划入口 | 拆解 CorePlanning 的请求准入、工具协议、上下文构建与展示；所有任务入口按会话角色进入同一治理路径 | 不再由不同入口各自实现分析/派工规则；KIM 状态来自实际运行，不能仅靠一段提示词或 UI 标签宣称启用 |
| 2.5 界面与应用用例分离 | 窗口菜单、快捷键、斜杠命令调用统一用例；界面订阅状态；命令注册信息驱动帮助与入口 | 清除界面中的重复业务判断；保留视觉定稿、快捷键与现有多窗口行为；显示缓存不反写权威状态 |
| 2.6 清理与规范验收 | 删除已替代实现、无消费者适配器和失效文档；按模块格式化，接入类型、错误处理、Promise 与导入边界检查 | 没有遗留的第二套执行路径；新代码遵循同一规范；生成资产/vendor 明确排除，例外必须说明原因 |

每批完成四件事：迁移实现与全部调用者、验证行为、删除被替代业务代码、更新架构/测试说明。不能把这四件事拆到遥远的后续阶段，长期依靠新旧双写维持运行。对仍有外部消费者的兼容入口，登记具体消费者和退出版本/条件，只做输入输出转换，不复制调度或权限规则。

数据迁移采用版本化 schema 与明确迁移函数；先备份再迁移，失败不覆盖原数据。如果当前批次无需变更格式，就保持格式不动。回退说明同时覆盖源码和数据：旧程序不能读取的新格式，不允许只回退程序后继续写入。

**阶段门槛：** 第一阶段登记的目标反向依赖与重复业务路径已收口；类型检查、适用的现有回归、关键边界测试及构建通过；基线测试数量只是参考，不能删掉失败用例凑通过。抽查普通请求和主控任务从入口到回执的实际路径，确认运行的是新结构。最终报告附模块对应表、已删除路径、保留兼容项及原因。未满足这些条件，不把“已经拆文件”称为重构完成。

### 第三阶段：Agent 编排可靠性与完整闭环验收

**目标：在统一结构上解决派工不准、漏派、等待不清楚、失败恢复和完成判定问题。** 修改业务负责人所在模块，避免在 UI、提示词和异常捕获处分别补救同一问题。

| 子步骤 | 改进内容 | 可验证结果 |
| --- | --- | --- |
| 3.1 统一工具协议 | 从同一领域 schema 生成模型参数和运行校验；迁移 work_json/checks_json 字符串协议；先确认各适配器支持的 schema 子集 | 必填项、能力 ID、约束和验收条件一致；错误返回字段路径/错误码/修正建议；不悄悄丢字段或修改授权 |
| 3.2 主控分析与分配 | 核查 KIM 对任务意图、约束、可拆分性和完成标准的输出；按窗口实际能力、项目、权限、忙闲和依赖分配 | 开启主控后无需用户反复提醒派工；任务有明确范围、负责人和验收；无合适窗口时明确等待原因，不虚报已派发 |
| 3.3 调度与时间语义 | 验证准入、依赖、并发、租约、取消、审批和恢复；分别记录排队、审批、模型响应、工具执行及整体耗时 | 每个非终态任务都有负责人、等待原因和后续处理规则；无重复执行、无永久静默卡住；测试观察期限与业务期限分开 |
| 3.4 角色与权限一致 | 由实际权限和当前角色生成工具可见菜单/能力视图；执行端仍独立强制检查；验证角色切换与工具清理 | 审查任务不会被推荐调用禁止写入/执行的工具；菜单变化不会扩大权限；拒绝、真实失败和恢复均有记录 |
| 3.5 错误、恢复与证据 | 实施下表的分类策略；任务/尝试/工具回执可关联，证据绑定具体产物版本 | 取消和重启后不盲目重放；失败不能被包装为成功；只有满足验收的实际结果才能使任务完成 |
| 3.6 最终构建验收 | 先确定性测试，再用最终构建做有限、固定的真实模型样本；形成用户能复查的报告 | 普通任务和多窗口均跑完整闭环；不能拿旧构建成功、单个子任务成功或“已开始运行”替代最终结果 |

错误与恢复必须统一实施：

| 情况 | 处理原则 |
| --- | --- |
| 参数/计划无效 | 执行前拒绝，返回结构化原因；允许预算内修订，但原始约束不能因修订消失 |
| 权限或审批拒绝 | 保留明确拒绝；需要改变方案或获得相应授权，不能自动换窗口绕过 |
| 网络/模型慢或失败 | 区分请求、等待和执行是否已发生；仅对可安全重试部分进行有界重试，遵守总预算，避免供应商与应用层叠加重试 |
| 容量不足/依赖未就绪/等待审批 | 显示具体等待原因及解除条件，允许取消；不能全部记为工具执行超时 |
| 实际工具执行失败 | 保留失败回执；根据已知副作用决定修正或停止，不把真实失败当作纯参数错误删除 |
| 写操作结果未知 | 先核对文件/进程/回执或进入人工处理；禁止自动重放可能重复产生副作用的操作 |
| 证据不足、产物版本变化 | 不得直接完成；补充验证或重新审查指定版本，不沿用失效结论 |

验收分两层，样本与预算在执行前固定：

- **确定性回归：** 覆盖同项目/多项目、多模型配置路由、依赖、并发、忙闲匹配、审批拒绝、取消、断网、输出截断、重启、存储损坏与空间不足；通过模拟时钟/故障注入验证超时和恢复，关键规则必须全部通过。能力层 Code/Data 的专门完善仍集中在第四阶段，不在此交替扩功能。
- **真实模型闭环：** 建议最低固定三类任务：单窗口 Code 任务、同项目主控多窗口协作、不同项目窗口的隔离与分配。每类至少两轮，包含串行和并发安排；多模型支持须在实际配置的组合上单列结果。明确预算、截止时间、预期产物、需要的审批及观察期限。仅有一个模型时如实列出未验证范围。

每轮记录源码/构建标识、模型配置（不含密钥）、样本编号、计划与派工结果、完整闭环耗时、审批次数及失败分类；列出全部尝试，包括失败，不反复重跑后仅展示成功。不用少量样本推导普遍成功率或稳定的 P95。

**阶段门槛：** 关键确定性回归通过；预定真实样本得到明确结果，所有成功声明均有完成及审查证据；旧的最终审查验收缺口必须在当前构建补齐。若关键路径失败，修复后重做受影响样本并保留旧记录，不能仅扩大超时、降低权限或放宽验收。尚未验证的平台/模型组合进入支持范围说明。第三阶段结束时交付一套能解释失败、可恢复、可核对的完整编排实现，不宣称任何模型永不出错。

- 每次变更说明问题、所在层、唯一事实来源、行为差异、测试与回退方式；结构整理先保持行为，协议调整单独记录兼容性。
